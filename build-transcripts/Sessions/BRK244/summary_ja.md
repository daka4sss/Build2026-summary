## 全体像

本セッションは約36分のブレイクアウト（レベル200）。AI エンジニアリングコミュニティを長年運営してきた Swix（swyx）が、コーディングエージェントの爆発的普及によってソフトウェア開発の在り方がどう変わりつつあるかを俯瞰し、「マルチエージェントのオーケストレーション（agent supervision／監督）こそが新しいシニアエンジニアのスキルだ」という主張を展開した。スライドベースの講演というより、Q&Aを多く挟む対話形式（登壇者自身が「インタラクティブだと聞いていた」と何度も会場に問いを投げる）で進んだ。

話の骨格は大きく3つ。（1）現状認識 — GitHub Copilot を含むあらゆるツールが「Conductor（エージェント司令塔）」型のUIに収斂しつつあること、モデル単体ではなく「モデル＋ハーネス」の時代に移ったこと。（2）ソフトウェア開発ライフサイクル（SDLC）の再構築 — IDE の死、PR から「prompt request」へ、人間レビューが消える「ダークファクトリー」、spec（仕様）駆動の開発。（3）インフラと研究の先行指標 — サンドボックス需要、CPU不足、超高速推論チップ（Talos の17,000 tokens/sec）、そしてリアルタイム性・ワールドモデルといった次の研究フロンティア。

Swix の一貫したメッセージは「コーディングで去年起きたことが、今年は知識労働すべてで起きる」というもの。開発者はその未来を最初に体験する特権的な立場にあり、超人的なコーダー（agents）は手に入ったが「超人的なレビュアー」はまだ存在しない、というギャップこそが価値の源泉だと締めくくった。なお自動字幕由来の固有名詞・数値には不確実なものが含まれるため、随所で注記する。

## チャプター1: 「すべてはConductorになる」現状認識（0:00頃）

冒頭、Microsoft をややからかう形でつかみを取りつつ、業界全体のUI収斂を指摘。

- 自己紹介: 「Hi everyone, I'm Swix.」
- 数週間前にローンチされた **GitHub Copilot アプリ**（VS Code を超えた Copilot の大型リブランド）を題材に、「最近ローンチされた他アプリと驚くほど似ている」と指摘。
- **「Everything is conductor（すべてはConductorになる）」**: Conductor がこの「エージェント司令塔（agents command centre）」というフォームファクタに最初に到達し、Cursor、Windsurf、Codex、GitHub が次々と同じ形にリブランドした。
- 皮肉として、自身がアドバイザーを務める **Cognition** も前日に同型の「agent command centre」を出荷したと言及（local-to-cloud のハンドオフ機能が特徴）。
- これは「想像力の欠如」ではなく、収斂が必然である例として **「カニ化（carcinization）」**（地球上でカニ型が独立に7回以上再発明された現象）を引き合いに出す。
- 注意の対象が「個々のエージェント管理」から移行している流れ: オートコンプリート → 個別ターミナル → 12個のターミナルをmux → より秩序立ったConductor型へ。
- 自身の作業も複数のCursorやClaude Codeインスタンスを横断する混沌としたもので、講演中に「GitHubトークンを公開してしまった、ローテーションしないと」と口にする一幕も（収録されている点を後段で再度ネタにする）。

## チャプター2: コミュニティで観測した6つのコアテーマ（2:16頃）

「なぜ我々はここにいるのか（why we're here）」を出発点に、AIエンジニアコミュニティ（パリ、ロンドン、マイアミ、シンガポールなど）で観測した変化を整理。「6つのコアテーマ」を伝えたかったと述べる（明示的な番号付き列挙ではなく語りの中で展開）。

- **FOMAT（Fear Of Missing Agent Time）**: ある登壇者の造語。エージェントの稼働時間を逃す不安から、深夜2時に起きてエージェントにEnterを押してまた寝る、といった「多相睡眠」的な働き方をする人がいる。
- **「Big model religion」からの脱却**: もはやモデル単体への信仰ではなく、**「モデル＋ハーネス（model plus harness）」の組み合わせ**が本質。開発者はハーネスを形作ることで強い影響力を持てる。
  - ハーネスの構成要素はプロンプトだけでなく、MCP、スキル、ワークフローなどへ拡張。チャット以外のUIが必要になっている。
- **モデルラボのハーネス／スウォーム志向への移行**: 各ラボが「純粋なモデル出力」から、ますます **swarm（群）指向**のハーネスへ移行。
  - 例: Kimi K2（自動字幕「Kimmy K2」）が数百の並列スウォームを実行。
  - 例: Anthropic（自動字幕「Tropic」）が100万行規模のコードベースを **Zig から Rust へ移植**する「embarrassingly parallel（恥ずかしいほど並列）」機能を発表。
- **人間の雇用とジョブセキュリティ**: この領域には多くの人間が引き続き雇われる。
- **モートはどこにあるか**: Claude Code のソースコードが丸ごとリークしても何も変わらなかった（Anthropic は依然として時価総額1兆ドル級になる）。競合ハーネスの作者たちも「リークから学ぶことは何もなく、自分たちも同じことをしていると確認しただけ」と語った。
  - 結論: **モートはモデルにもエージェントハーネスにもない** → 価値は「複数エージェントのオーケストレーション」と「人間とエージェントのマインドメルド（mind meld）」にある。

## チャプター4: SDLCの再構築① — IDEの死とPRから「prompt request」へ（8:09頃）

ソフトウェア開発ライフサイクル（SDLC）の各段階がどう変わるかを順に検討。

- **IDEの死**: Steve Yegge（自動字幕「Steve Yagi」、Gastown の作者、有名な「Platform Rant」の著者）が「2026年にIDEは死ぬ」と予言した講演を引用。実際そのとおりになり、「everything is conductor」のカニ化が直後に起きた。
  - 前日にインタビューした Satya（Microsoft をAIプラットフォーム化したい意向）と Yegge の Platform Rant を重ねる示唆。
- **PRの次の段階**: 多エージェントオーケストレーションの次は **PR（Pull Request）**。
  - 2つのバージョン: オープンソース版と社内チーム版。オープンソース版が最も脅威にさらされる（悪意ある／意図と合わないPRの流入経路）。
  - 提案: **「pull request」ではなく「prompt request」**。メンテナはコードではなく「intent（意図）」さえあればよく、そこから自分で適応させられる。
- **PRの先 — goal loop / Ralph loop**: 「Ralph Wiggum loop」が昨年バイラル化し、今や主要コーディングエージェントに採用。これがエージェントが自分の作業を検証する**クローズドループ**につながる。
- goal（ゴール）の本質: エージェントに「どうやるか」ではなく「**どう評価するか・いつ止めるか**」を伝えること。これは人間がやっていることの原始的な形を書き下したもの。

## チャプター5: ダークファクトリーと「人間レビューゼロ」（10:21頃 / Q&A中心）

会場との対話を通じて、人間レビューが消えた世界の輪郭を描く。

- **Light factory vs Dark factory**:
  - **Software factory / token factory**: パイプラインで大量のソフトウェアを生産する概念。
  - **Light factory（ライトファクトリー）**: 多くの人間がレビューする工場。
  - **Dark factory（ダークファクトリー）**: もう人間がレビューしない工場。「very scary（とても怖い）」が、多エージェントオーケストレーションが要求するため到来する。レビューが唯一のボトルネックになる。
- **Q&A: 外側ループ（ユーザー受容・変更管理）の堅牢化** — 「ideas → validation → user change management」。
  - 内側ループ（internal loop）と外側ループ（external loop）がある。
  - 強い **spec（仕様）**へ収斂させる必要があり、関心が「生のコード配信」より一段上に移る。プロンプトが検証手段になる。
- **Swiss cheese model（スイスチーズモデル）**: 今年トップの記事の一つ（Latent Space / AI Engineer の寄稿者プログラム発）。spec ＋ 強力なテストスイートでリグレッションを防ぐ。
  - それだけでは不十分 → オンライン評価（online eval）、機能フラグ（feature flagging）、段階的ロールアウト（progressive rollouts）という外側ループが必要。
  - 「これらは元々良いソフトウェアエンジニアリングの実践だが、エージェントによって**Uber や Facebook の10%規模**で出荷するようになるため、はるかに重要になる」。大規模組織の実践を前倒しで全員が必要とする。

## チャプター6: ハーネスエンジニアリングとSpec駆動開発（13:10頃）

ダークファクトリー領域の実例と、「マークダウンと英語でプログラミングする」spec駆動の手法。

- **Ryan（自動字幕「Ryan Le Papolo」、OpenAI、不確実）**の **「harness engineering」**記事: 1日に約10億トークン（約 $10,000/日）を、コードもなく人間レビューもなく出荷。
- **OpenAI Symphony**（最近オープンソース化）: 強い構造を持つアプローチ。唯一の方法ではなく、StrongDM など他社もダークファクトリー領域で革新中。
- **「超人的なコーダーはいるが、超人的なレビュアーはまだいない」**: エージェントの落ち度というより、人間側のコミュニケーション帯域が足りない（「neural link がまだない」ため機械は推測するしかない）。
- **対策は高速サイクル**: ある事例では100万行・大型アプリでも **コンパイル時間1分未満**を死守。高速サイクル → 高速フィードバック → 人間とエージェントの強い整合（alignment）。
- **Symphony のspecの実態**: 巨大なマークダウンファイル群。約2,000行のプロンプトからなる「ゴールドスタンダードのspec」。
  - 焦点は **「narrow waist（くびれ）」** — API契約、モジュール間のサーフェス、型、データ構造。これがモデルの起こすエントロピーを封じ込め、逸脱検証の手段になる。
  - 「ほとんどの人はこれをやらない。私もやらない。運が良くて200行書く程度」と自己開示。
- **Microsoft のビジョン（Swixの解釈）**: 今はフロンティアモデル（GPT、Claude）を使うが、最終的には **自社のspecで訓練した自分専用／自社専用モデル**を持ち、高価なモデルを使わずに済むようになる。
  - 「良いエージェントプラットフォームは**あなたの味方**であるべきで、OpenAI の味方であってはならない」 → **「エージェントラボ vs モデルラボ」**論争が中心的議題。

## チャプター8: インフラ転換 — CPU不足と超高速推論（22:00頃）

エージェントがインフラに与える影響を、CPU/GPU比率と推論速度の観点で。

- **GPU:CPU 比率の変化**: かつては主に訓練（training）で **8:1**。エージェントの普及で **1:1** へ。これが **CPU不足**を招く。
  - 出典: Intel CEO（自動字幕「Le Bhutan」、不確実）の直近決算コール。Sam Altman の「AI推論企業（training だけでなく）」発言も引用。
- **超高速推論**: 並列大量エージェントは「できるだけ速く終わらせたい」。
  - Cognition は **Cerebras**（自動字幕「Cerebrous」）と密接に協業（「three, 1.5」「3C2」など製品名は自動字幕で不確実）、数千 tokens/sec を志向。
  - 一般的な推論速度の目安: 50〜100 tokens/sec。
  - **推論速度ベンチマーク（Swixが提示）**:

| チップ／システム | 位置づけ（自動字幕由来、数値は登壇者の口述） |
|---|---|
| NVIDIA H200 / B200、Grok（Groqの誤記の可能性）、Cerebras | 「速い」とされる既存勢 |
| **Talos** | **約17,000 tokens/sec** で突出 |

  - 「誇張ではなく実際に見た」。近く **300,000 tokens/sec** の推論が見えてくる（コモディティトークン用途、フロンティアロジックではない）。

- **10倍ごとに使い方が変わる**: 推論速度・モデル規模の各10倍が、利用習慣・作れる製品・オープン/クローズドモデルの選択を変える。「これはMooreの法則的に確実に起きる。インフラ投資は既に済んでいる」。

## チャプター9: ハードウェア寿命とモデルサイズの「small」のインフレ（Q&A、26:00〜29:00頃）

会場からの「では次に我々を押し上げるのは何か（モデルか）」「シリコンに焼いたモデルの陳腐化」という問いへの応答。

- **「これは全部ハードウェアであり研究ではない」**: 速度向上はモデル訓練側から見れば最適化に過ぎない。生の量子化と数値精度の研究はあるが、速度面で最も面白い研究は **画像・動画生成コミュニティ**から来ている。「数十億ドル規模の最高峰のポーカーゲーム」。
- **重みをシリコンに焼く問題**: ほとんどの企業は実重み（weights）をシリコンに刻んでいない。それをやっているのは現状 **Talos のみ**。Cerebras や Groq は「白帽（white hat）」で、短期的勝利のために重みを焼き込まない。
- **チップの長寿命化**: 「テールは非常に長い」。GPT-4.1 や Llama 3 を今も使う人がいる。動くアプリは変える理由がなく、安く速くなるだけ。
  - チップの償却期間はかつて **3〜4年** → 今や **約8年**へ延長。H100 の平均価格は上昇（「melted up」）。4年前のチップでも価値が増している。
- **モデルサイズの「small」のインフレ**: Mistral の Chief Research Officer（ポッドキャストゲスト）によれば **24B が今や「small」**。
  - 推移: 1〜2B → 7〜8B → 24B が small。いずれ100B が small に。
  - トップエンドは GPT-4 の約1兆パラメータから、最新の Mixtral 級で10兆超へ。「あと何桁も残っていない。残りは研究の領域」。

## チャプター10: 次の研究フロンティア — リアルタイム性とワールドモデル（30:35頃）

残り時間で、今後を左右する研究アジェンダを概観。「等しい重みではない」と断りつつ列挙。

- **メモリ／継続学習（continual learning）**: 今後5年語られ続けるが大きな変化は見えにくい（投機的）。
- **リアルタイム（real time）= 今まさに起きている本命**:
  - GPT-4o デモで約束されたが実現しなかった「低遅延ボイス」。
  - Swix の記事 **「semi-async valley of death（半非同期の死の谷）」**: AIの作業を眺めるだけで価値を出せない、コンテキストスイッチもできない不気味な遅延帯。フローに留まって超高速か、完全非同期かのどちらかしかなく、中間は無い。
  - 理想の働き方: バックグラウンドにタスクを投げつつ、**メインスレッドはディープワーク**（最も難しく価値ある集中作業）に充てる。それ以外はコモディティ推論へ。
  - これまでのモデル進化は「推論時間の増加（2時間→15時間の自律）」ばかり。だが **2000ms → 200ms → 20ms** のレイテンシ削減こそ欲しい。
  - これに取り組むのは現状 **Thinking Machines** のみ（「interaction small models」のデモ動画。未リリースだが「ここにアルファがある」と世界に示した）。
  - チップ投資（300,000 tokens/sec）で擬似的にレイテンシは下げられるが「真にインタラクティブ」ではない。真のインタラクティブとは、**訓練データ自体にマイクロバッチの相互作用が組み込まれている**こと。
- **エージェントがあらゆるモダリティを飲み込む**:
  - 動画生成は「プロンプト→1パスで動画」から、**エージェントが動画モデルをオーケストレーションする「video agents」**へ。特定ドメイン向けにオーケストレータを訓練する意味は過小評価されている。
- **ワールドモデル（world models）= ダークホース**: 現状モデルは「中央値のRLHF人間／RL環境が報酬を与えそうなもの」を予測するが、**ユーザーが何を望み何を好むかのワールドモデル**（presence of mind / theory of mind の第2レベルの知能）が欠けている。

## まとめ

最後に Swix は **「Agent work paradox（エージェント労働のパラドックス）」**を提示してクロージングした。エージェントはかつてないほど多くの仕事をこなしているのに、人間もかつてないほど働いている — それは正常であり、未来の圧縮をいち早く受け止める報われる立場だと述べた。そして「**AIエンジニアリングは最後の仕事（the last job）**だ。なぜなら他のすべての仕事を自動化するのがあなたたちだから」と締めた。

- モートはモデルにもハーネスにもない。価値は **マルチエージェントのオーケストレーション（agent supervision）** と、人間とエージェントの整合（mind meld）にある。
- **超人的なコーダーは手に入ったが、超人的なレビュアーはまだいない** — このギャップ（特にダークファクトリーの「人間レビューゼロ」化）が今後の主戦場。
- コーディングで昨年起きたことが、今年は知識労働すべてで起きる。開発者はその未来を最初に体験する。

### エンジニア向け次のアクション
1. 自分の作業を「単一エージェント → マルチエージェント → 自前オーケストレータ」のどの段階にあるか把握し、次段階を計画する（多くの人はマルチエージェント段階）。
2. **spec（仕様）駆動**へ移行する。API契約・型・データ構造という narrow waist を厳密に記述し、OpenAI Symphony のような詳細specを参考にする。
3. ダークファクトリー化に備え、**強力なテストスイート＋オンライン評価＋機能フラグ＋段階的ロールアウト**を前倒しで整備する（大規模組織の実践を10%規模で導入）。
4. **環境のフルforkが可能なサンドボックス基盤**（serverless志向）を検討する。
5. 推論速度・モデルサイズの「10倍ごと」を前提に製品・アーキテクチャを設計する（Talos / Cerebras / Groq などの動向を追う）。
6. レイテンシ（リアルタイム性）を重視し、バックグラウンドのコモディティ推論と、メインスレッドのディープワークを分離するワークフローを設計する。
7. 「あなたの味方であるエージェントプラットフォーム」を選ぶ視点（エージェントラボ vs モデルラボの論争）を持つ。最終的には自社specで訓練した専用モデルへ。
