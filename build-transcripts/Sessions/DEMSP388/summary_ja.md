## 全体像

本セッションは Anthropic の Applied AI Architect である Caroline Matthews が登壇し、Microsoft Foundry 上で Claude Code を活用したエージェンティック・コーディング（agentic coding）の最前線を紹介するデモ中心のセッション（約21分）。「エージェントが触れる範囲」「エージェントが自分の正しさを判断する方法」「エージェントが知覚できるもの」「エージェントがいつ・どこで動くか」という4つのフロンティアを軸に構成されており、各フロンティアに対応したライブデモが行われた。

すべてのデモは Microsoft Foundry（Azure AI Foundry）上で動作しており、エンタープライズの安全性・コンプライアンス・Microsoft スタックとの統合を維持しながら、パイロットから本番への移行を加速できることが強調された。

## チャプター3: 4つのフロンティアと事前タスク起動（0:03頃）

エージェンティック・コーディングの進化を阻む「4つのフロンティア（限界点）」を定義し、それぞれを押し広げることが価値創出の鍵だと説明。

1. **何をエージェントに触らせるか（What agents are allowed to touch）** — どこまで自律的に動かし、どこで人間が介入すべきか
2. **エージェントが自分の正しさをどう知るか（How will your agent know when it's right?）** — 人間が全PRをレビューしていたらスケールしない。AIによるAI生成コードの自律的レビューが必要
3. **エージェントが知覚できるもの（What agents can perceive）** — テキスト・diffのみでなく、視覚情報・ブラウザ操作・コンピューター操作
4. **いつ・どこでエージェントが動くか（When and where the agents run）** — 数分から数時間・数日規模への拡張、複数サーフェスでの継続動作

ここで Caroline は「最後のデモ（フロンティア4）を先に起動してしまう」と宣言し、Claude Code 上でアーケードゲームの自律生成タスクをキックオフ。「プレゼン中に並行して動かし続ける」というライブデモを演出した。

## チャプター4: フロンティア1 — Auto Mode デモ（0:05頃）

**課題の提示**: エージェントを動かしてコーヒーを取りに行ったら、戻ったときに「ファイルを編集してよいですか？」「README を更新してよいですか？」「テストを実行してよいですか？」と許可確認のメッセージが溜まっていた、という典型的な問題。これまでの回避策は `--dangerously-skip-permissions`（通称：なんでも許可フラグ）を使うことだったが、文字通り危険で誰にも勧められない。

**新機能: Auto Mode（Research Preview）**

Auto Mode は、ユーザーの許可リクエストとモデルの間に**クラシファイアー**を挟み込む仕組み。クラシファイアーが操作のリスクを自動判断し、リスクが低い操作（ファイル読み込み・テスト実行など）は許可を求めずに自動実行、リスクが高い操作（任意の Bash コマンド実行など破壊的なもの）は引き続きユーザーに通知する。

**デモの流れ**:
1. 通常モードで FastAPI アプリに新しいエンドポイントを追加するタスクを実行 → 複数回の許可確認プロンプトが発生し、人間がボトルネックになる様子を実演
2. Claude Code の「Rewind」機能でセッションを元の状態にロールバック
3. Auto Mode（画面下部に黄色のバッジで表示）に切り替えて同じタスクを再実行 → 今度は人間が一切介入しなくても完了

Auto Mode の精度指標として「False Positive Rate 0.4%（本来許可すべき操作を不必要にブロックする率）」および「Over-eager Actions（本来確認すべき操作を無許可で実行してしまう率）」が現時点の改善課題として言及された。「まだ完璧ではないが、以前に比べて大きな進歩」と述べ、Research Preview として提供中であることを明示。

**新機能（Research Preview）**: Claude Code Auto Mode

## チャプター5: フロンティア2 — Oracle（エージェント・コードレビュー）デモ（0:09頃）

**課題の提示**: AIが生成したコードを人間が一行一行レビューしていてはスケールしない。AIエージェント同士でコードを生成・レビューする仕組みが必要。

**ケーススタディの共有**: 16並列エージェントで数万行規模のコードを用いてCコンパイラを構築しようとした試みは「コストが大きく、セッション数が膨大になり、失敗に終わった」。ここから得た教訓が「Planner → Generator → Evaluator」の3ロール分離アーキテクチャ。

**推奨アーキテクチャ**:
- **Planner エージェント**: タスクを分解
- **Generator エージェント**: コードを実際に記述
- **Evaluator エージェント（Oracle）**: 生成されたコードを独立してレビュー・テスト・判定

ポイントは「コードを書いたエージェント自身にレビューさせない」こと。コンパイラ事例では GCC でコンパイル結果を検証するという明確な正解判定基準（ground truth oracle）があったが、あらゆるユースケースでそれが用意できるわけではないとしつつ、まず評価基準の設計に時間を投資することを強く推奨した。

**デモの流れ（split terminal で左右2エージェント並列表示）**:
1. 左側 Generator（Auto Mode）に「友人との夕食代を割り勘する `bill_split` 関数を書いて」と指示 → 動作するが「センント（小数点以下の金額）を切り捨てる実装」というやや不完全なコードを生成
2. 右側 Evaluator（Oracle）に生成されたコードを渡し、「批判的にレビューせよ」と指示 → Oracle は「基本動作はするが、端数処理の改善が必要」と指摘し、自身でテストケースを作成して実行 → テスト失敗を検出
3. Generator にフィードバックを渡し、修正を指示 → コードが改善される

「Evaluator の設計こそが最重要投資先。コーディングを始める前に評価基準を整備せよ」というメッセージで締めくくった。

## チャプター6: フロンティア3 — 高解像度画像解析・ペネトレーション・テスト デモ（0:13頃）

**課題の提示**: エージェントはテキスト・diffを読めるが、人間が実際に見ているもの（ブラウザ画面・アプリのUI）を見られると更に強力になる。

**新機能（Claude Opus 4.8）**: 高解像度画像の取り込み能力の大幅向上。これにより、ブラウザの実 Chrome（headless スクレイプではなくフル Chrome）や Computer Use（OS全体の操作）を通じてエージェントが視覚的な文脈を取得できる。iOS シミュレーターを使ったアプリ開発への応用例として、エージェントがシミュレーターを起動してUIの変化を確認しながら修正するユースケースも言及。

**具体的な成果事例（Expo社によるペネトレーション・テスト）**:
- Sonnet 4.6（旧バージョンモデル。発言では "Opus 4.6" と誤称されているが文脈上以前のモデルを指していると推測）でのエージェンティック・ペネトレーション・テスト成功率: **58%**
- Claude Opus 4.8 の高解像度画像解析能力導入後の成功率: **98%**

**デモの流れ（Azure AI Foundry のプレイグラウンドで Claude Opus 4.8 を使用）**:
1. 「セキュリティエンジニアとしてリスクを評価せよ」というシステムプロンプトを設定したモデルに対し、怪しいアプリのスクリーンショットを添付してリクエスト送信
2. 聴衆にも5秒間同じ画面を見せて「リスクを見つけられるか」というクイズ → ほぼ誰も見つけられなかった
3. Claude が3.4秒で回答 → スクリーンショット上に「secrets」「password」といった明示的なヒントはないにもかかわらず、推論によって複数のセキュリティリスクを特定

「画像を取り込んだ上で推論を適用できる。それが大きな差を生む」とまとめた。

## チャプター7: フロンティア4 — 動的ワークフロー・マルチエージェント並列実行デモ（0:16頃）

**課題の提示**: 数分・数時間・数日規模でエージェントを継続稼働させたい。ターミナルでタスクをキックオフして会議に行き、電話でプロンプト承認をして、デスクに戻ったら作業が完了している、という開発体験を実現したい。

**新機能（Claude Opus 4.8）: Dynamic Workflows**（発表直前の新機能。セッション時点でプレゼン資料にはまだ未掲載と Caroline が言及）

サブエージェントを動的に管理・調整するための仕組み。Claude Code 上で `/workflows` コマンドで確認できる。

**デモの結果（セッション開始時にキックオフしたバックグラウンドタスクの成果確認）**:

指示内容: 「アーケードゲームを作れ。あまり話しかけてくるな。プロジェクターで表示されるので見映えを考慮せよ」

15分の講演中に以下が自律的に完了:
1. **デザイン生成エージェント × 3**がそれぞれ独立してアーケードゲームのデザインを考案
   - Agent 1: "Neon Drift"
   - Agent 2: "Pulse Runner"
   - Agent 3: "Neon Ascent"
2. **ピッカー（Judge）エージェント**が3案を比較評価し、"Neon Ascent" を選択
3. **ビルドエージェント**が選ばれたデザインを実装
4. **テストエージェント × 4**が並列でテストを実行（ブラウザを開いてビジュアル確認を含む）
5. 不具合を発見して自動修正

最終的に動作するアーケードゲームが生成・公開され、セッション中にプロジェクターで動作を実演（音声付き。最初は音声なしで起動されて一瞬戸惑ったが、直後に音声確認）。「コードを数行書いて `build an arcade game` と言うだけ。私はほぼ何もしていない」と Caroline は述べた。

**その他の継続実行を支える機能として言及**:
- Loops（定期的なタスク実行）
- Scheduled Tasks（スケジュール実行）
- Ultra Plan（より深い計画生成モード）
- Voice（音声でエージェントに指示できる機能）

## チャプター8: まとめ（0:20頃）

クロージングメッセージとして「エージェントが人間を完全に置き換えることは目標ではない」と明言。人間はリスクの高いもの・価値の高い判断が必要なものに集中し、その他の繰り返しタスクはエージェントに任せるという Human-in-the-loop の再定義を提案。

「コーディングをより人間的なものにする」という方向性でエージェンティック・フロンティアを押し広げ続けるというビジョンで締めくくった。
