## 全体像

本セッション「Build secure and enterprise-ready agents with Agent 365」は、急速に普及するAIエージェントをエンタープライズ環境で安全・安定して運用するための制御プレーン「**Agent 365**」を紹介するセッションである。

IDCの予測によれば、2028年までに組織内に13億ものエージェントが存在するようになるとされており、その数は世界の国の数を上回る。しかし現実には「エージェントを構築・利用している」とほぼ全員が手を挙げる一方、「エージェントが企業レディで、観測可能で、セキュアで、ガバナンスが効いている」と答えられる参加者はほとんどいなかった（登壇者談：「1人だけ手が挙がった」）。

Agent 365 はこのギャップを埋めるためのソリューションである。Microsoft ファーストパーティのエージェントだけでなく、LangChain・AWS Bedrock・Google Vertex AI など**任意のフレームワーク・クラウドで構築されたエージェント**にも対応する「エージェントのための制御プレーン」として位置づけられている。セッション全体は、概念説明・ライブデモ（SDK 統合、管理コンソール操作）・パートナー事例（Genspark）の三部構成で進んだ。

## 1. エージェントのエンタープライズ化における課題（0:00 頃）

Neda がオーディエンスへの挙手クイズを交えながら課題を提起した。エージェントには大きく以下の3種類がある。

- **SaaS エージェント**：アプリに組み込まれた既製品エージェント
- **エンドポイント／カスタムエージェント**：開発者がさまざまなフレームワーク（LangChain、AWS、Gemini など）で自作するエージェント
- **クラウドエージェント**：各種プラットフォーム上に構築されるエージェント

これら多種多様なエージェントに共通する運用上の問いかけとして以下が挙げられた。

- 組織内の全エージェントを**発見・管理**できているか？
- エージェントが意図どおりに**振る舞っている**か（インテント逸脱・ツール誤用はないか）？
- データの**過剰共有・漏洩**は発生していないか？
- **ガバナンスと監査**に対応できているか？

これを解決するためのキーワードとして「**Observed（可観測）・Govern（統治）・Secure（保護）**」の3本柱が示された。

## 2. Agent 365 のアーキテクチャと3本柱（2:30 頃）

Kendra がバトンを引き継ぎ、Agent 365 のコンセプトを詳述した。

### 3つの柱

Observed（可観測）: 全エージェントのインベントリ・レジストリへの登録。採用トレンド・利用状況・構築プラットフォームの把握。リスク軽減のためのアクション推奨。

Govern（統治）: ガードレールの実装。リスクレベルに応じたポリシー適用。イノベーションを止めるのではなく「加速させるための」ガバナンス。

Secure（保護）: Microsoft Entra（ID管理）・Defender（リアルタイム脅威検出）・Purview（データガバナンス）・Microsoft Intune（シャドーAI検出）の統合。フルログによるインシデント追跡と類似脆弱性の事前検出。

### Agent 365 が対応するエージェントの種類

1. **Microsoft ネイティブエージェント**：Copilot Studio などで構築されたエージェントはネイティブで Agent 365 に統合。
2. **パートナーエージェント**：Workday・Genspark など、SDK を介してプロアクティブに統合されたサードパーティエージェント。
3. **カスタムエージェント**：LangChain・AWS・Google 等で自作されたエージェントは **Agent 365 SDK** を利用してオンボーディング。
4. **外部プラットフォームのエージェント**：Amazon Bedrock・Google Vertex AI など連携プラットフォームのエージェントは **Registry Sync** 機能で可視化のみを目的として取り込む。

## 3. 主要概念：Agent Blueprint と Agent Identity（11:20 頃）

デモ前に Kendra が2つの重要な概念を解説した。

### Agent Blueprint（エージェントブループリント）

エージェントへの**再利用可能な指示書**。「どのツールを使えるか」「どのデータにアクセスできるか」「どのルール・ガードレールが適用されるか」を定義する。エージェントのレシピとして機能し、複数のエージェントインスタンスを同一ブループリントから生成できる。

### Agent Identity（エージェントアイデンティティ）

サービスプリンシパルではなく、**ユーザーIDに近い形でエージェントに与えられる固有のID**。エージェントはアプリのように構築されるが、**ユーザーのように振る舞う**ため、それに適したID管理が必要。認証方式は2種類：

- **ユーザーの代理（On behalf of）**：ユーザーがエージェントを呼び出した際、そのユーザーのクレデンシャルとパーミッションを引き継ぐ。
- **エージェント独自のユーザーID（Agent user identity）**：エージェントが自身のIDとパーミッションで単独動作する。

## 4. デモ1：Agent 365 SDK でカスタムエージェントをオンボーディング（13:25 頃）

Aarthi が VS Code を使いながらデモを実演した。

### シナリオ

LangChain + Node.js（TypeScript）で構築した**トラベルエージェント**（出発地・目的地・日程を入力するとホテル3件・フライト3件・レストラン情報を返す）を Agent 365 に対応させる。Agent 365 は Microsoft エージェント専用ではないことを示すために、あえて LangChain を選んだと Aarthi は説明した。

### 手順（GitHub Copilot または Claude Code 等のコーディングエージェントを利用）

1. **スラッシュスキルの呼び出し**：VS Code 内で `/skills agent365` を実行。6つの Agent 365 スキルが表示される（今後も追加予定）。
2. **「make」スキルの選択**：エージェントを Agent 365 対応にする包括的なスキル。エージェントフォルダを起点に「make this agent ready for Agent 365」と指示するだけ。
3. **スタックの自動検出**：コーディングエージェントが Node.js + LangChain（TypeScript）であることを自動判別。
4. **前提条件チェック**：Agent 365 CLI の最新版インストール、Azure CLI ログイン状態の確認、対象テナントの特定。
5. **実行計画の生成と実行**（約10分）：
   - Agent 365 パッケージのインストール
   - **Blueprint の作成**（Entra 設定の追加）
   - **Observability の設定**（OpenTelemetry のワイヤリング）
   - **Work IQ サーバーの設定**：Word・OneDrive の MCP サーバーを追加（エージェントがドキュメントを作成し、OneDrive に書き込めるようにする）
   - **通知エンドポイントの設定**：Teams チャットへの応答、Word ドキュメント内の @メンションへの応答が可能に
   - マニフェストファイルの生成

この手順により、エージェントは Azure・GCP・AWS・任意のクラウドでホスティングしつつ、Agent 365 の機能を完全に活用できる状態になる。実際のエージェントIDは管理者が Microsoft 365 Admin Center でエージェントを「アクティベート」した時点で作成される。

## 5. デモ2：エンドユーザー体験とエージェントの「同僚化」（18:44 頃）

### ユーザー視点のデモ

エンドユーザーとして Teams 内のアプリ一覧からトラベルエージェントの**インスタンスを作成**（「ひとりのエージェントを雇う」という表現が使われた）。Teams チャットでエージェントに旅行プランを依頼（Seattle から Austin、Build カンファレンス後）。ホテル・フライト・レストランの提案を受け取るとともに、**編集可能な Word ドキュメントの自動生成**を確認した。

続いて Word ドキュメント内で **@メンション** によりエージェントに追加依頼（コーヒーショップのリストを要求）。エージェントがドキュメントのコメントとして返答した。「同僚に Teams で話しかけるのと同様に、ドキュメント内でエージェントを @メンションできる」体験を実演し、エージェントが一人の「デジタル従業員」として組織に溶け込んでいる様子を示した。

### オブザーバビリティの確認

- エンドユーザー自身も**エージェントとのやり取りの履歴・成功/失敗**を確認できる。
- 管理者（admin）視点では：ブループリントごとの複数インスタンス一覧、各インスタンスのアクティビティ、ユーザーリストを確認可能。

## 6. デモ3：Microsoft 365 Admin Center によるエージェントガバナンス（25:09 頃）

Kendra が Admin Center のデモに移行した。ログイン時に「Wrong button（ボタン押し間違い）」というハプニングがあり、会場に笑いが起きた。

### オーバービューページ

テナント全体のエージェント総数、ユーザー数（人間のみ、エージェントIDを除く）、**ランタイム時間（total runtime hours）** などのハイレベル指標を表示。対応アクション一覧（CTA）として次の項目が表示される。

- 承認待ちエージェントの処理
- リスクが検出されたエージェントの確認
- **オーナーなしエージェント**の管理（「エージェントスプロール」の抑制）
- 例外（runtime エラー）が発生したエージェントの一覧

また、エージェントの採用数推移グラフや上位利用エージェントも表示される。

### エージェントレジストリ

テナント内の全エージェントを一覧表示。Microsoft エージェントのみならず Workday・Genspark などのサードパーティエージェントも混在して表示される。各エージェントの詳細ページで確認できる情報：

- エージェントの説明・パブリッシュ日・最終更新日・パブリッシャー・オーナー・エージェントID
- **エージェント指示書（system prompt）**の参照
- **IDヒストリー**（Bot ID・Blueprint ID・Entra Agent ID）
- 共有ユーザーリスト・適用済みポリシー・パーミッション一覧
- **アクティビティビュー**（総ユーザー数・セッション数・例外数・ランタイム時間・成功セッション率）
- **依存関係グラフ（ビジュアルビュー）**：マルチエージェント構成でのブラストラディアスを把握可能（例：「このエージェントをブロックしたら他に何が壊れるか」を事前確認）

### ルール（Rules）機能

ライフサイクル管理アクションの自動化が可能。

- オーナーが退職した場合に自動で上長へ再割り当て
- リスク検出時にエージェントを自動ブロック

今後数四半期でさらに機能強化予定と明言された。

### テンプレート（Templates）機能

Kendra が「ヒーロー機能」と呼んだ機能。Entra・Defender・Purview・SharePoint にまたがるカスタムポリシーを**1つの再利用可能なテンプレート**に集約する。デフォルトテンプレートと任意のカスタムテンプレートを作成可能。含められるポリシー例：アクセスパッケージ・条件付きアクセス・DLP 保護・ライフサイクル管理保護。エージェントのパブリッシュ承認フローで選択・適用される。

### エージェントのパブリッシュフロー

1. 公開対象ユーザーの選択（全ユーザー / 一部ユーザー / ストアで発見可能）
2. データとツールの確認（リスクレベルの把握）
3. テンプレートの適用（デフォルト or カスタム）
4. パーミッションのレビュー・承認
5. 公開完了

### Registry Sync 機能

Amazon Bedrock・Google Vertex AI など外部プラットフォームの認証情報を設定し、そのプラットフォーム上のエージェントを**可視化目的でレジストリに取り込む**。外部プラットフォームで保持しているパーミッション（例：削除権限）もそのまま利用可能。シャドーAIの検出範囲を Defender と連携して 22以上のローカルプラットフォームに拡大する計画も発表（将来ロードマップ）。マルチテナント対応も開発中と明言された。

## 7. パートナー事例：Genspark による Agent 365 統合（38:44 頃）

Genspark 共同創業者の **Ray** が登壇し、Agent 365 との統合経緯を共有した。

**Genspark（Jasma）** は「知識労働者のための統合 AI ワークスペース」であり、すでに2000以上の組織が日常業務で活用しているとのこと。

### ユースケースの多様性への対応

- **Sarah（財務部門）**：Board deck 作成のためのサマリーや簡易分析 → チャットベースの AI ツールで対応可能
- **Tom（データ分析担当）**：200MB 超の CSV に対する大規模計算 → 専用 VM の重量級コンピュートが必要

これら異なるバックエンドを柔軟に組み合わせつつ、エンタープライズとしての統制を維持するために Agent 365 の Python SDK を採用した。

### Agent 365 の3つのプリミティブとして活用

1. **Identity（Entra による認証）**：初回認証ではなく、**リクエスト（メッセージ）ごとに認証**を実施。Teams グループチャットで自社エージェントに別テナントのユーザーがアクセスしようとした際、Entra ID で不正ユーザーを検出しリクエストを拒否する仕組みを構築。独自の認証レイヤーを追加で構築する必要なし。

2. **MCP による M365 統合**：Agent 365 が提供する PowerPoint・Outlook・Word の MCP サーバーを活用し、エージェントがリクエストに応じてドキュメントを生成し、ユーザーや自エージェントの OneDrive に書き込む。独自のストレージレイヤーが不要になった。

3. **Observability / Purview / ライフサイクル管理**：エージェントの全アクティビティ・推論・ロケーション情報が Microsoft Purview に自動ログ記録。エンタープライズ全体で適用済みの Purview の機密ラベルポリシーがエージェントにも自動適用され、機密情報の漏洩をブロック。統合ログは同一の Microsoft API を通じて SQL クエリで分析可能。

## まとめ

Agent 365 は「どこで構築されたエージェントでも」対応する、エンタープライズ向けのエージェント制御プレーンである。開発者は Agent 365 SDK（またはコーディングエージェントによるスキル実行）でエージェントを数十分でオンボーディングでき、IT 管理者は Microsoft 365 Admin Center から全エージェントの可視化・ガバナンス・セキュリティポリシー適用を一元管理できる。

### 発表された主な新機能・新要素

Agent 365 SDK（Python / Node.js 対応確認）: サードパーティ・カスタムエージェントを Agent 365 に統合するためのラッパー SDK。公開済み（詳細な GA/Preview 区分は未明確）。

Agent 365 Coding Agent Skills: VS Code 等のコーディングエージェントからワンコマンドでエージェントを Agent 365 対応にするスキルセット。公開済み（今後も追加予定）。

Agent Blueprint: エージェントの再利用可能な定義・レシピ。公開済み。

Agent Identity（Entra ベース）: エージェントをユーザーと同等のIDで管理し、代理認証または独立認証に対応。公開済み。

Registry Sync: Amazon Bedrock・Google Vertex AI など外部プラットフォームのエージェントを可視化目的で取り込む。公開済み。

テンプレート（Templates）: Entra・Defender・Purview・SharePoint のポリシーをまとめた再利用可能な承認テンプレート。ヒーロー機能として強調。公開済み。

ルール（Rules）: ライフサイクル管理（オーナー再割り当て・自動ブロック等）の自動化。今後数四半期で機能強化予定。

Work IQ MCP サーバー: Word・OneDrive 等の M365 サービスをエージェントが利用するための MCP サーバー群。公開済み。

シャドーAI検出の拡大（22以上のプラットフォーム）: Defender 連携によるローカルプラットフォームのエージェント検出範囲拡大。将来ロードマップ。

マルチテナント対応: 複数テナントを跨いだエージェント管理。開発中。
