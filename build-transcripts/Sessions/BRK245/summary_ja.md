## 全体像

本セッションは「ビルドするものを作るもの（the thing that builds the thing）」というテーマのもと、登壇者のPeterが自身の大規模OSS（OpenClaw）を維持・開発する中で、コーディングエージェント（Codex CLI や Claude Code）を支援するために自作してきたツール群を紹介する内容です。どのように「エージェントが自律的に動けるループを閉じるか」を中心に据えた実践的なトークです。

Peterは「今日の開発者の仕事は自分がコードを速く書くことではなく、エージェントが速く動けるようにすることだ」という信念をベースに、痛みを感じるたびにツールを作り、それが複利的に積み重なっていく様子を語ります。紹介されるツールはすべて「自分が苦痛だったから作った」という実用主義で生まれており、コードレビューを一切しない"スロップ"ベースで量産されている点も印象的です。

セッションは質疑応答まで含めて約42分。製品アナウンスではなく個人開発者の実践知の共有という性格が強く、新機能の発表（GA/Preview）は含まれませんが、オープンソースメンテナーやコーディングエージェントのパワーユーザーにとって再現性の高いノウハウが凝縮されています。

## チャプター2: OpenClaw爆発とIssue地獄 — Claude Reaperの誕生（0:58頃）

OpenClawが急成長し、GitHubのIssueとPRが爆発的に増加した問題への対処。

**背景と課題**

- GitHubのオープンIssue数が表示上5,000でキャップされる仕様に気づかず、実際には10,000件以上存在していた。
- 現代のPRはほとんどがエージェント生成（スロップ）であり、コントリビューターが既存Issueを確認せずに重複投稿するケースが大半。
- 「PRの実態はプロンプトリクエスト（prompt request）に変わった」と表現。IssueもPRも本質的には「何かを変えてほしいというシグナル」。
- CodeRabbitなどの既存ツールは試したが「レビューを返すだけ」で不十分だった。

**解決策: Claude Reaper の自作**

- GitHub Actionとして動作するツール。
- 動作原理:
  1. 誰かがIssueまたはPRを開くと、クラウド上でCodexセッションを起動。
  2. プロジェクトのビジョン・方針を記述した vision.md ファイルを読み込む（「これは受け入れる/これは受け入れない」を明文化）。
  3. ルールに基づいてIssueにコメントするか、Issueをクローズする。
- vision.md はすべてのOSSプロジェクトに作成しており、標準プロンプトの一部として必ず読み込ませている。
- 成果: 約15,000件のIssueをクローズ。
- さらに週1回（またはそれ以上の頻度で）全IssueとPRに対してClaude Reaperを再実行する仕組みを導入。マージ済みコミットで解決済みのIssueを自動クローズし、Issue投稿者に「mainで修正済みです」と自動返信する。
- Discord通知: 再実行結果（「3か月前のIssueをクローズした」等）がDiscordに流れてくる。

## チャプター3: メンテナー管理ダッシュボードとDiscordCrawl（8:24頃）

**メンテナーレポートダッシュボード**

- GitHubのIssue/PRアクティビティだけでなく、Discordの会話参加度も含めて評価するダッシュボードを自作（非公開）。
- 「良いメンテナーとはコードをプッシュするだけでなくディスカッションに参加する人」という信念から。

**DiscCrawl の自作**

- Discordには公開APIでデータを取得する手段がないため、Botトークンを使ったクローラーを自作。
- データ配布の問題: Botトークンをすべてのメンテナーへそのまま配布したくないため、GitHubをバックアップ用データストレージとして使用（Discordデータをシリアライズして定期的にGitHubへコミット）。
- Botトークンを持たないメンテナーも、このGitHubリポジトリを代替データソースとして使える。

**プロジェクト横断インテリジェンス**

- Codexを自分のプロジェクトフォルダ全体に対して起動し「今やるべきことは何か？」と質問する運用。
- DiscCrawlのデータと組み合わせて「ユーザーが最も叫んでいる問題と、オープンIssue/PRの相関トップ5」を抽出し、vision.mdと照らし合わせて自律作業可能なものを並列実行。

**Issue Browser の自作**

- Codexが生成するIssueリストのURLをクリックするのが「数クリック多くて苦痛だった」ため、専用UIを自作。
- Codexが生成するフォーマットのばらつきに対応するため、都度パーサーを拡張。
- 「ツールを作るためのツールを作るべきだ」という本セッションのコアメッセージを体現するエピソード。

## チャプター4: GitHub APIレート制限問題 — Octopusの誕生（17:05頃）

**背景**

- 個人アカウントのトークンは1時間あたり5,000リクエスト。複数のCodexセッションを並列で動かすとすぐにレート制限に到達。
- チームメンバーのAshleyがリセットボタンを手動クリックしていたが、深夜作業時には頼めない状況があった。
- 「苛立ちこそ最高の問題解決の動機」と笑いを交えながら語る。

**Octopus の自作**

- GitHub Appをインストールすると1時間あたり15,000トークンが利用可能になる仕組みを活用。
- Cloudflare Workers上にデプロイしたプロキシを構築:
  - 読み取り専用・非変更操作（パブリックリポジトリ） → GitHub Appのトークンを使用。
  - 書き込み・変更系操作 → 個人トークンを使用。
- gh CLI コマンドをOctopus経由でラップするシンプルな設計。
- CloudflareのデプロイもCodexに「こういうものが欲しい」と説明するだけで、Cloudflareコンソールのブラウザ操作まで含めてエージェントが自動構成（セキュリティ設定は自分でレビュー推奨）。
- 教訓: 「痛みを感じたらメタレベルに上がり、痛みを解消する方法を考えよ」 — 解決策は自分だけでなくチーム全体を助け、複利的に積み重なる。

## チャプター5: テスト実行の重さ問題 — CrabBoxの誕生（20:06頃）

**背景**

- テスト実行時間: 10秒→5分と肥大化。並列化で1分に短縮したが、40コア未満のマシンでは「コンピューターが溶ける」と苦情。
- Blacksmith（テスト用クラウドVM提供サービス）を試したが1日2時間以上のダウンタイムがあり、依存しすぎていたためダウン中は生産性がゼロになった。

**CrabBox の自作**

- 名前の由来: 「変な甲殻類系の名前を維持しなければ」（Octopusとの統一感）
- 設計原理:
  1. クラウド上に軽量な使い捨てVMをスピンアップ。
  2. ローカルの変更を非同期でVMに同期。
  3. リポジトリはVM上に既にチェックアウト済みの状態で提供。
  4. テストをVM上で実行、CPUコストをクラウドへオフロード。
- フォールオーバー: メインプロバイダー障害時にAWSや別クラウドへ自動切り替え。コミュニティからのPRで現在20以上のプロバイダーに対応。
- クロスプラットフォーム対応: 複数OSのボックスを並列起動（「全OSでテスト実行」とエージェントに一言で3〜4ボックス並列起動）。
- Web VNCによるUIテスト: VM上でブラウザを起動し、Web VNCでエージェントが直接UIを操作（スクリーンショット・クリック・タイプのMCPツール経由）。
- 推薦: 「auto-review と CrabBox、この2つだけを持ち帰るとしたら試してほしい」

## チャプター7: 自動コードレビュー — auto-reviewとCLAUDE.md最適化（26:23頃）

**問題: 手動レビューループの苦痛**

- Codexで実装後 /review → 10〜20分待ち → 3件の問題発見 → 修正 → /review 再実行 → 10〜30分待ち → 2件の新問題…を繰り返す。
- ある日、Line（メッセージングアプリ）サポートを追加する作業で1日中このループを回し続けた。
- 「自分がclanker（エージェント）になっている感覚」という表現。

**auto-review の自作**

- AGENT.md（CLAUDE.md相当のエージェント指示ファイル）に1行追記するだけ:
  「コミットまたはPRを作成する前に、auto-reviewを実行していなければ実行すること。」
- Codexが自分自身をCLIコマンド経由で呼び出すことで新鮮なコンテキストでのレビューを実現。
- 再帰呼び出しループのバグが発生したことがあるが修正済み。
- 多ラウンドの自動レビューを信頼性高く実行する仕組みが完成。
- コンテキスト管理のコツ: エージェントを呼び出すCLIコマンドに「実行すべきコマンド」を渡すだけで新鮮なコンテキストが得られる。

**CLAUDE.md / AGENT.md のベストプラクティス**

- 「clanker自身にclankerへの文章を書かせよ」という逆転の発想。
- ワークフロー:
  1. 欲しいものをエージェントに説明する。
  2. エージェントが自分の言葉でAGENT.MDに書く。
  3. 定期的に「AGENT.MDで混乱している箇所は？」とエージェントに質問し、矛盾を整理する。
- 矛盾はトークンの無駄遣いで品質を下げるためクリーンアップが重要。
- 不変条件（invariant）を記述することが重要: 例えば「プラグインファイルはシステム実行中にランダムに編集されない」といった前提をエージェントは知らないため、防御的すぎるコードを書いてしまう。このような前提知識を積極的に書き込む。
- 各セッション開始時にコンテキストはほぼリセットされるため、書いておけば書いておくほど良い結果が得られる。

## チャプター8: PRのプロンプト透明性 — Prompt Requestスキルの導入（31:38頃）

**問題**

- 1行のプロンプトから10ページのコードが生成される時代、PRへの「作業量」が外から見えない。
- コントリビューターガイドラインで「使ったプロンプトを添付してください」とお願いしたが、便利な仕組みがなく誰も守らなかった（人の怠惰に逆らう設計は機能しない）。

**解決策: Prompt Request スキルの自作**

- OpenClawに貢献してPRを送ると、エージェントが自動で質問: 「プロンプトのプライバシーフィルタリング済みのバージョンを送信しますか？送ると、PRのレビューが優先されます」
- ユーザーが yes と入力するだけで:
  1. エージェントがディスク上の自分自身のトランスクリプトを検索。
  2. 関連する部分のみにトランスクリプトをトリミング。
  3. PRにアタッチ。
- 効果: 「4語5トークンのプロンプトで作ったPR」と「数時間かけて議論を重ねたPR」を一目で区別可能。
- 名言: 「今、私たちを制限しているのはもはや知性ではない。モデルは十分に賢い。制限しているのは私たちの想像力と、それをどう使うかだ」

## チャプター9: 既存コードベースの全体レビュー — CorePatch（34:52頃）

auto-reviewで新規コードの品質は上がったが、過去に蓄積した「レビューなしコード」という技術的負債の問題に直面します。

**問題**

- 既存の100万行のコードベースに /review を一括適用することはコンテキストサイズの都合上不可能。
- 「何年も前のコードにどれだけ問題があるか」を知るのが怖いが、知らないままにしておくのも不安。

**CorePatch の自作**

- 原理: 大規模コードベースを50個程度のサブセクション（機能単位等）に分割し、それぞれを個別にエージェントへレビューさせる。
- 実行するだけで「大量の興味深い発見が得られることを保証する」。
- 制限: 完全には仕上がっておらず、数千のCodexセッションにスケールする場合は無制限トークンが必要。コードベース整理用途では十分効果的。

## チャプター11: Q&A（39:28頃）

**Q1（匿名）**: ツール群がエンタープライズ化するにつれ、他ツールへの依存が新ツール開発の邪魔になることはないか？

**A（Peter）**: 今のところそれは起きていない。むしろ逆で、既存ツール群があることで新ツール開発が加速する。「エージェントにパターンマッチングをさせればよい（あの問題はあそこで既に解いた、と伝えるだけ）」。失敗したツールからも学びがあり、その学びが次のツールに生きる。git履歴を読ませてコンテキストを把握させる手法も有効。

**Q2（Divya、Solutions Engineer）**: 「自分はたくさんの仕事を抱えていてツールを作る時間がない」という問い。

**A（Peter）**: 石器時代に四角い車輪から丸い車輪への切り替えを「忙しいからできない」と断るミームに例える。これらのツールは「超スロップ」でいい。1つのCodexセッションに「この作業でこういう苦痛があった。それを解消するツールをこういうイメージで作れ」と伝えるだけで十分。プログラミング言語も何も指定しなくていい（自分はGoを使っているが、好きというわけではなく「エージェントがGoで速く書けるから」）。

**ボーナス: ウィスパーフロー**

- チームで口頭で議論しながら「ウィスパーフローボタンを押す」とCodexが会話を聞きながら実装を開始する。

## まとめ

### セッションの結論

本セッションはMicrosoft BuildのBRK系セッションとしては珍しく、スライドレスに近い形式で、登壇者Peter自身のOSSメンテナンス現場から生まれたツールを10種類以上にわたって紹介しました。すべてのツールに共通するのは:

1. 苛立ちが発明の母: 苦痛を感じたら即ツール化。完璧さは不要。
2. ループを閉じる: エージェントが自律的に動き、結果を検証し、人間の承認だけを求める設計。
3. 複利の力: 各ツールが他のツールを前提として使われ、指数的に効率が向上する。
4. エージェントに書かせる: CLAUDE.md等の指示ファイルはエージェント自身に書かせ、エージェント視点で最適化する。

本セッションは個人開発者の実践共有セッションであり、MicrosoftやAnthropic等の製品としての公式アナウンスは含まれていません。すべてのツールは登壇者Peterが個人/チームで開発したオープンソースプロジェクトです。

### 次のアクション

- auto-review と CrabBox を最優先で試す（登壇者の推薦）。
- vision.md を自プロジェクトのルートに作成し、エージェントへの方針を明文化する。
- CLAUDE.md（AGENT.md）の内容をエージェント自身に書かせ・レビューさせる習慣をつける。
- 繰り返し作業で「苛立ち」を感じたら即座にツール化することを試みる。
- OSSメンテナーはClaude Reaperのコンセプトを参考に、GitHub Actions と coding agent によるIssue自動トリアージを導入する。
