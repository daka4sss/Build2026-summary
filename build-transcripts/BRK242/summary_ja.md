## 全体像

本セッションは、エンタープライズ向けエージェント開発における「ツール統合の複雑さ」と「ドキュメント解析の精度」という2つの大きな課題に正面から取り組んだ技術セッションである。Microsoft Build Day 2 の午後に行われ、会場は満員。Maria が冒頭で「体調が少し悪い（風邪気味）」と断りを入れながら進行した。

前半は Maria が **Microsoft Foundry の新機能 Toolbox** を紹介。複数のMCPサーバーやAPI、スキル、コネクターを「ひとつのバンドル」にまとめ、統一エンドポイント経由でどのエージェントからでも利用できる仕組みを解説した。後半は Joe が **Content Understanding**（コンテンツ理解サービス）を掘り下げ、PDFや動画、Office文書など多様な形式のコンテンツをエージェントが高精度に活用できる仕組みを実演した。

セッション全体を貫くテーマは「エージェントに正しいツールと正確なコンテキストを届ける」ことであり、コンテキストウィンドウの肥大化防止（token節約）、ガバナンス、マルチモーダル文書解析の3点が強調された。

## エージェントプラットフォームとしての Microsoft Foundry（0:01頃）

Maria は最初に Microsoft のエージェントプラットフォーム全体像を示した。

- **GitHub** でビルド → **Foundry** をプラットフォームとして利用 → エージェントのランタイム最適化とツール整備 → **Microsoft 365** で配布
- Foundry が提供するもの: エージェントサービス、モデル、IQ ツール、コントロールプレーン。クラウドからエッジまでのライフサイクル管理。
- Foundry Tools はすべてのツールタイプを一か所に集約するための「シングルハブ」として設計されている。

## ツールエコシステムが抱える3つの課題（0:02頃）

ツールとエージェントが急増する中、顧客から寄せられる主な問題は3つ。

**ツールの多様化と混乱**: かつてはMCPだけだったが、現在は skills、plugins、OpenAPI specs、Logic App コネクター、CLIs、hooks、agent-to-agent (A2A) など多種多様なツールタイプが存在し、今後さらに増え続ける見通し。Maria は「'foobar X bar' のようなものまで出てくるだろう」と笑いを交えながら表現した。

**ツールディスカバリーの本質**: 「ツールディスカバリー」とはレジストリで検索して正しいツールを見つけることではなく、**限られたトークン数でタスクを完了するのに最適なツールを選択すること**である。すべてのツール定義をコンテキストウィンドウに詰め込む従来の方法は、コストとパフォーマンスの両面で問題がある。

**セキュリティとガバナンス**: ツールはデータベースや本番コード、APIに直接アクセスするため、「誰がどのツールを使えるか」を細かく制御する必要がある。例として「Maria より Linda の方が職責が高いため、Linda にはより広いツールアクセスを与えたい」というユースケースが挙げられた。

さらに、6個の統合を持つ1つのエージェント（Entra、SharePoint、チケッティング、カスタムMCP、Teams、Blob Storage、Azure Search）を例に取り、これが顧客サポート・請求・ネットワーク・在庫エージェントへと広がると数百の統合になること、しかも各ツールは独自のアイデンティティ・プロトコル・認証情報管理を持つため、開発者がエージェント開発より統合作業に時間を費やす悪循環が生まれることを指摘した。

## Toolbox の概念と4つの柱（0:09頃）

Maria は課題解決策として **Toolbox**（ツールボックス）を発表した。Satya Nadella の基調講演でも言及された新カテゴリの機能。

**Toolbox の定義**: 「Foundry で管理された再利用可能なツールのバンドルであり、ツールタイプに関わらず単一の一貫したインターフェースを通じてエージェントが利用できる。」

3つのキーワード:
- **Reusable（再利用可能）**: 一度作成すれば、すべてのエージェントで使い回せる。Build once, use everywhere。
- **Managed（管理済み）**: Foundry がライフサイクル全体を管理。
- **Consistent interface（一貫したインターフェース）**: 下層のツールタイプを意識せず、単一の OAuth 認証・単一エンドポイントでアクセスできる。

4つの柱:

| 柱 | 内容 |
|---|---|
| **Build** | ツールを名前付きの再利用可能なバンドルとして作成・設定・発行する |
| **Discover** | エージェントがプロンプトをもとに必要なツールだけを取得し、不要なものをコンテキストウィンドウに読み込まない |
| **Consume** | MCP 互換のエンドポイントですべてのツールをどのエージェントランタイムにも公開する |
| **Govern** | 集中管理された認証・オブザーバビリティ・ポリシー・ガードレールを提供する |

主要機能:
- **Tool Search**: Toolbox 内部でメタデータを検索し、タスク完了に必要なツールだけを動的に取得するプロトコル。10件登録されていても必要な1件のみをコンテキストウィンドウにロードする。
- **統一エンドポイント**: MCP 互換の単一 URL として払い出される。Hosted Agents、GitHub Copilot CLI/SDK、Claude Code（準備中）、Microsoft Copilot Studio などで利用可能。
- **Governed Dashboard**（将来提供）: ツール呼び出しの詳細可視化ダッシュボード。

## デモ① — Toolbox の構築と Tool Search の動作（0:12頃）

Maria がライブデモを実施。デモ環境のパーミッション問題でブラウザを切り替えるトラブルが発生したが、「CEOだけがデモゴーストを持つわけではない、私もそれを持っている」とジョークで乗り越え、最終的に成功させた。

**Toolbox なしの場合（Before）**: MCPエンドポイントをひとつずつ個別設定する必要があり、たった3つのMCPサーバーを設定しただけで設定コード（OAuth・認証情報・プロトコル設定）が行33〜行104まで膨れ上がった。Maria は「このコードはAIが100%生成したものなので実際には動きません」とユーモアを交えて補足。

**Toolbox ありの場合（After）**: 設定は数行で完結。認証を設定し各サーバーをToolboxに割り当てるだけで、統一エンドポイントのURLが自動生成される。

**Skills のアップロードデモ**: Foundry ポータルの「Build → Tools → Skills」からカスタムスキル（アーキテクチャ図作成スキル）をアップロード。成功後、プロジェクト内の全エージェントからそのスキルが利用可能になる。

**Browser Automation の発表**: **本日よりGA（"available today"）** の新ツール「Browser Automation」（Playwright ベース）を発表。Webスクレイピングやフォームへの自動入力が可能。ライブデモで Microsoft Forms の自動入力を実演。

**FIBI エージェントのデモ**: Toolbox の統一エンドポイントを Azure Container Apps 上でホストされた「FIBI エージェント（Fiber Optic Inspection/Billing エージェント）」に接続。Activity ビューで Tool Search が10件から1件だけを選択してコンテキストウィンドウにロードする挙動を確認。

## Content Understanding の概要と位置づけ（0:22頃）

Joe Flick がバトンを引き継ぎ、エージェントが「ドキュメント内コンテンツ」をどう扱うかを解説。

実世界のコンテンツはAPIレスポンスだけではない。PDF、PowerPoint、動画など多様な形式が存在し、エージェントがこれらを読み込もうとすると、内容の取りこぼし・テーブルデータの取得失敗・コストとトークン消費の増大などが発生する。

**Content Understanding の定義**: 「雑然としたマルチモーダルコンテンツを、クリーンで構造化されたエージェント対応出力に変換するサービス」。**GA 済み**（約6か月前にGA、約1年半の本番実績）。

顧客事例として以下が紹介された:
- **Wolters Kluwer（税務・法務・医療向け専門ツール）**: CCH Axcess Tax 製品で税務フォームや財務文書のインジェストと構造化処理に利用。税務申告処理のエンドツーエンド自動化を実現。
- **Data Sniper（監査・財務向けエージェンティックプラットフォーム）**: AI抽出機能の基盤として利用。任意の文書を Excel に構造化データとして直接取り込み、「より迅速なレビュー、信頼性の高い証拠、trustworthy AI」を実現。

## Content Understanding のパイプライン詳解と今後の改善（0:25頃）

Content Understanding は単一パイプラインで **Parse → Classify → Extract** の3ステップを実行する。

**Parse（解析）**: Microsoftが20年にわたって磨いてきたOCRおよびレイアウト技術を適用。多言語対応、テーブルの詳細抽出、しわくちゃのページからの抽出にも対応。画像・動画・PDF・メールファイル・ZIPファイルなど、あらゆるモダリティに対応。今後の改善として、図表（チャート・ダイアグラム）の構造化マークダウン表現の抽出を強化。

**Classify（分類）**: ドキュメントの種別を識別し論理単位に分割する。多くのエンタープライズ文書は単体ではなく申請書類パッケージ・ケースファイルなど複合的な形式であり、Content Understanding は必要な部分を特定して不要な部分を除外できる。**2026年7月予定**: ページ境界だけでなくセクション境界でも分割可能に。

**Extract（抽出）**: キーバリューペア、構造化出力、信頼度スコアを生成。各抽出フィールドは文書内のバウンディングボックス・単語・文章にグラウンディングされており出典の追跡が可能。信頼度スコアにより「高信頼なら自動承認、低信頼なら人間レビューへルーティング」という自動化ワークフローを実現できる。

**2026年7月に予定される改善**:
- Knowledge sources を用いた新しいトレーニングプロセス（特定ドキュメントのサンプルを与えて抽出精度を向上）
- 新プリビルトアナライザー（大幅なコスト削減・トークン削減版）
- **Agentic Extraction**（エージェンティック抽出）

## Agentic Extraction の発表（Coming July）（0:30頃）

Joe が Content Understanding の新モード「**Agentic Extraction**」を紹介（録画デモで実演）。

標準的な抽出は「ドキュメント内の特定の値を見つける」ことは得意だが、「答えを推論で構築する必要がある」ケース（例: コントラクト全体と修正履歴を横断して適用条項を特定する、障害の根本原因を分析するなど）には不十分。

Agentic Extraction はスキーマに質問セットを定義すると、Content Understanding がツール群を使いながら証拠コーパスを横断的に推論しループを繰り返して回答を構築する。トレースビューで「画像への後続質問」「計算・コード実行」も確認できる。

録画デモでは光ファイバーケーブル障害シナリオを使用し、「根本原因は何か」「修正費用はいくらか」「予算内か」という質問セットに対して、Agentic Extraction が証拠を特定・計算しながら高精度な根本原因分析を自動生成するデモを実施（Demo 331、QRコードでリポジトリ公開）。

## デモ② — Content Understanding を使った FIBI エージェント（0:33頃）

Joe がライブデモで4つのシナリオを比較実験した。

**シナリオ1（Content Understanding なし）**: 光ファイバーF3の計測ログPDFに「特定日付の計測値は？」と質問。実際には計測値が欠損しているにもかかわらず、エージェントは「46」と不正な回答（ハルシネーション）を生成。簡易パーサーが欠損値を読み飛ばしたことが原因。

**シナリオ2（Content Understanding Standard モード）**: Content Understanding がPDFを解析してテーブルを構造化マークダウンに変換。欠損値が「値なし」として明示されたため、エージェントが「記録なし」と正しく回答。また図表のデータもJSON形式に変換され、チャート内容への質問も可能になった。

**シナリオ3（DOCX ファイル + Context Provider）**: 通常はDOCX非対応のエージェントハーネスに、Content Understanding を Context Provider として有効化することで任意ファイル形式に対応。LangChain プリミティブとしても利用可能。

**シナリオ4（アナライザーによるビジネスルールのエンコード）**: ワークオーダーPDFで「フィールドテクニシャンは誰か？」と質問。ガイダンスなしではサイト連絡先 John Smith を誤答。Content Understanding Studio でアナライザーに「テクニシャン判定ルール」を記述することで、正しい回答（Jay Martinez）を安定取得できるようになった。
