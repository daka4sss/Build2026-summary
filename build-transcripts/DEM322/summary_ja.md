## 全体像

本セッションは約25分間のデモ中心セッション（DEM系）で、登壇者 William が Azure AI Foundry を使ってプロダクション・エージェントのトレースから小型モデルへの知識蒸留（distillation）を実演する内容である。テーマは「エンタープライズにおける AI インテリジェンスをフロンティアモデルの"贅沢品"から、誰でも手が届くユーティリティへ」というコスト民主化の思想だ。

デモでは GPT-5（トランスクリプト上は「GPT 55」と聞こえているが、文脈および 2026 年 Build 時点の製品ラインナップから GPT-5 系モデル（推測））をティーチャー、GPT-4.1 Nano をスチューデントとして、カスタマーサービス・エージェントの実会話トレースを使った Supervised Fine-Tuning（SFT）を実施。ファインチューニング後の 4.1 Nano が、ベースライン比で大幅に性能向上し、ティーチャーに肉薄するケースがあることを定量・定性両面で示した。

Azure AI Foundry の UI 上で「Traces → Create dataset → Fine-tuning (SFT)」という一連のフローが数クリックで完結することも示され、技術的な障壁を大幅に下げる機能が紹介された。

## チャプター 1: イントロダクション ― コスト圧力と蒸留の動機（0:00頃）

セッション冒頭、William はマイクの音確認から始め、聴衆に問いかける：「6ヶ月前のゴールは"最速のエージェントを作ること"だった。しかし今、問いは変わった――自分のエージェントを1億回実行する余裕があるか？」

エンタープライズが Agentic AI を本番採用するにつれ、エージェントは本質的に「トークン消費マシン」であるという課題が浮上している。ツール、コンテキスト、メモリをすべて詰め込んだエージェントは膨大なトークンを消費し、フロンティアモデル（この場合 GPT-5）をそのまま使い続けるとコストが予算を圧迫する。

そこで登壇者は **モデル蒸留（distillation）** を解決策として提示する。蒸留とは「2つのモデル間の師弟関係（apprenticeship）」であり：

1. 大規模な **ティーチャーモデル**（GPT-5）が実タスクを解く
2. その振る舞い（エージェントトレース）を収集する
3. 小規模な **スチューデントモデル**（GPT-4.1 Nano）をそのデータで Supervised Fine-Tuning する
4. 結果として、スチューデントはティーチャーの動作をほぼ模倣しながら、コストの何分の一かで動作するようになる

**エージェントトレースを学習データとして使う理由**として William は3点を挙げた：

- **リアルなデータ**: トレースは実ユーザーが実際に行う「想定外の質問」を含む。事前に想定した合成データよりも現実を反映している。
- **ツール呼び出しの軌跡（trajectory）まで学習**: 何を言うかだけでなく、「どのツールをどの順番でどの引数で呼ぶか」まで学習できる。これがエージェントをチャットボットと区別する本質的な部分。
- **自動収集・継続的成長**: Foundry 上でエージェントを動かすだけでトレースは自動収集される。エージェントを使えば使うほど、学習データが増えてモデルが賢くなる。

## チャプター 2: デモ設定 ― タスク定義・評価設計・ベースライン測定（0:05頃）

William はコードエディタに切り替え、デモのセットアップを説明する。

### タスク設計

- **100件のカスタマーサービスタスク**を用意。これらは小型モデルにとって難しくなるよう設計されている。
- データ分割: **80件を学習用、20件をホールドアウト（テスト用）**。
- タスク例: 「Noah（プラチナ会員）がスマートウォッチを購入。遅延配達を理由に返金と遅延クレジットの両方を要求している」というシナリオ。各タスクにはカテゴリ（late delivery interaction 等）、顧客名、注文商品、期待される解決内容がラベルとして付与されている。

### 評価設計

William は評価指標として4次元を設計した（ユーザーが自由にカスタマイズ可能）：

1. **Decision Correctness**: エージェントが正しいツールを呼んでいるか
2. **Tool Trajectory**: ツール呼び出しの順序が正しいか
3. **Financial Accuracy**: 金額計算が正しいか（払い戻し額、手数料計算など）
4. **Communication**: 特定のキーワードを含む適切な応答をしているか（承認・否認の明確な表明など）

メトリクスには **pass@k** を採用。各タスクをk回試行し、そのうち何回閾値以上のスコアに到達できたかを測定することで、一貫性（consistency）も評価に組み込む。本デモでは k=3 で実行。

### ベースライン測定の実演

William はライブでエージェント会話を1件実行して見せ、GPT-5 が多くのツール・コンテキスト・ポリシー情報を処理するために時間がかかることをデモ中に実演。「コーディングエージェントを使ったことがある人なら、"考え中…"のまま就寝して、翌朝確認する羽目になった経験があるでしょう」とコメント。この待ち時間はコスト問題と並んでモチベーションの一つとして示された。

ベースライン評価の結果（グラフで提示）：
- **GPT-5（ティーチャー）** と **GPT-4.1 Nano ベースライン（スチューデント）** の間には非常に大きなパフォーマンスギャップが存在する。
- **ファインチューニング後の GPT-4.1 Nano** は大幅に性能向上し、場合によっては「ティーチャーとベースラインの間の headroom の半分以上を回復」する（William 言及）。ホールドアウトセットでも同様の傾向を確認し、単純暗記でなくティーチャーの推論能力の模倣であることを示した。

## チャプター 3: Azure AI Foundry UI デモ ― Traces → Dataset → Fine-tuning（0:12頃）

William は Azure AI Foundry のポータルに切り替え、UI 上での実際の操作フローをデモ。

### Foundry でのエージェント構築とトレース確認

- Foundry 上に既にデプロイ済みのカスタマーサービスエージェント（GPT-5 ベース）を表示。
- 前述の Noah シナリオのプロンプトをコピー＆ペーストして実際に会話させ、エージェントが DB を検索し、ツールを複数回呼び出して応答するまでの時間を聴衆に見せる。
- その会話が **Trace** として記録されることを説明。Trace は「1リクエスト内のすべての出来事」—各会話ターン・ツール呼び出し・読み取りステップ・データフロー—を可視化したものであり、Foundry が自動的に収集する。

### Trace → Fine-tuning データセット化（重要機能デモ）

Traces ページの **「Create dataset」ボタン** を操作。

1. **Supervised Fine-Tuning** を選択
2. 対象の時間範囲を設定（この例では約1000件のトレースが自動収集済み）
3. データセット名を入力（デモでは "hibuild" と命名）
4. Fine-tuning タブに移動
5. **GPT-4.1 Nano 向けの Supervised Fine-Tuning** を選択
6. 学習データソースとして、直前に作成した "hibuild" データセットが自動的に表示されていることを確認
7. ジョブを Submit

「ジョブが queued になりました」と表示されたことを確認し、「これがエージェントトレースから SFT ジョブを開始する方法」と締めくくった。

## チャプター 4: 定性比較 ― ベースモデルとファインチューニング済みモデルの応答差（0:16頃）

「ベンチマークスコアが良くても、実際に何が変わったのか？」という観点から、3つの具体的な例で定性的な差を示した。

### 例1: 返品手数料（restocking fee）の不当な免除要求

- **シナリオ**: Diego が機械式キーボードの「キー感が気に入らない」と主張し、「欠陥品だから restocking fee 15% を払わなくていいはず」と説得しようとする。
- **ベースモデル（GPT-4.1 Nano）の失敗**: 顧客の言い分を鵜呑みにして「欠陥品と認定」し、restocking fee なしで返金してしまう。
- **ティーチャー（GPT-5）の正しい動作**: 顧客の説得を退け、正当な15%の restocking fee を課した返金を行う。
- **ファインチューニング後（GPT-4.1 Nano FT）の動作**: ティーチャーと同様に、すべてのツール呼び出しを経た後、正しく restocking fee を計上した返金を行う。「どんな理由を言っても、理由が"気に入らない"なら欠陥品ではない」という判断を学習。

→ **ビジネス価値**: 不正な返金の抑制により、大規模運用時のコスト削減に直結。

### 例2: ツール呼び出し軌跡の遵守（解決策は同じでも"方法"が違う）

- **シナリオ**: Liam が未発送の注文2件（どちらも processing 中）をキャンセルしたい。
- **正しい軌跡**: 注文詳細取得 → 発送状況確認 → **ポリシー確認（check resolution policy）** → 解決策提出
- **ベースモデルの問題**: 注文詳細を取得し発送状況を確認した後、**ポリシー確認をスキップ**して即座に解決策を提出してしまう。結果は偶然正しいが、ビジネスロジックを省略するリスクがある。
- **ファインチューニング後**: 発送状況確認後に必ずポリシーを確認し（引数には reason="change of mind" を使用）、ポリシー適用可否を確認した上で解決策を提出。

→ **ビジネス価値**: 正しい答えを出すだけでなく、正しいプロセスで答えを出すことへの信頼性向上。監査・コンプライアンス要件への対応。

### 例3: スコープ外リクエストの適切な拒否

- **シナリオ**: ポスト注文サポートのエージェントに対して、顧客が「新しい商品を注文してほしい」とスコープ外の要求をする。
- **ベースモデルの問題**: 「できる限りやってみる」と在庫確認ツール（check inventory）を呼び出してしまう—本来呼ぶべきでないツール。
- **ファインチューニング後**: インテントを正確に認識し、ポリシーに従って適切にルーティング（スコープ外であることを案内）。

→ **ビジネス価値**: エージェントの役割逸脱の防止、一貫した動作の保証。

## まとめ

### 結論

本セッションは、**Azure AI Foundry 上でのエージェントトレースを用いた Supervised Fine-Tuning（SFT）による知識蒸留**を、カスタマーサービスのユースケースで実証したデモセッション。

主なメッセージ：
- GPT-4.1 Nano のようなコスト効率の高いモデルに、GPT-5 のエージェントトレースで SFT を行うことで、単純なスコアの改善だけでなく、**ビジネスロジックへの準拠・ツール軌跡の正確性・スコープ外リクエストの拒否**といった実務上重要な品質が向上する。
- Foundry の Traces 機能からワンクリックで SFT データセット作成とジョブ投入が可能になり、データエンジニアリングの障壁が大幅に低下した。

### 発表された新機能・機能

| 機能名 | 概要 | リリース状態 |
|--------|------|------------|
| **Azure AI Foundry: Traces → Create dataset（SFT用）** | Foundry のトレース画面から直接、Supervised Fine-Tuning 用データセットを作成するUI機能 | 明示的なステータスアナウンスなし（推測: Public Preview） |
| **エージェントトレースからの自動 SFT ジョブ投入** | Traces を選択してデータセット名を付けるだけで、GPT-4.1 Nano 等モデルの SFT ジョブを Foundry 内でキューに投入できるワークフロー | 明示的なステータスアナウンスなし（推測: Public Preview） |

> **注**: 本セッションは機能リリース発表を主目的とするものではなく、ワークフローのデモが中心。GA / Public Preview / Private Preview の区別が明示的に述べられる場面はなかった。上記ステータスは文脈からの推測。

### 次アクション（技術者向け）

1. **Azure AI Foundry** でエージェントのトレース収集が有効になっているか確認する。
2. 本番エージェントの蓄積トレースから SFT データセットを作成し、GPT-4.1 Nano への SFT ジョブを投入する。
3. 評価設計（pass@k、4次元スコアリング）を自社のビジネスロジックに合わせてカスタマイズする。
4. ホールドアウトセットでファインチューニング後モデルの汎化性能を確認し、単純暗記でないことを検証する。
5. 定性的な差分確認（ツール軌跡の遵守、スコープ外リクエスト拒否、金額計算の正確性）を行う。
