**登壇者**: Scott Hanselman（Microsoft DevDiv）、Mark Russinovich（Microsoft CTO / Azure）、Steve Sanderson（Blazor・Knockout.js 作者）、Cassidy Williams（フロントエンドエンジニア）、Swyx（AI Engineer World's Fair 主催）、Simon Willison（Datasette・LLM ツール作者）、Karuana Gatimu（MC／スポンサー取材担当）、Adrian Macias（AMD）、Bryan Hiestand（Intel）、Stephen Mccullough（NVIDIA）、Vivek Chauhan（Fireworks AI）、Ana Schafer（Qualcomm）

## 全体像

本セッションは「Scott and Mark Learn To...」ポッドキャストのライブ版として企画された公開ショー形式の枠で、テーマは「Vibe Check（バイブスチェック）」だ。Scott Hanselman が Mark Russinovich に今日の内容をまったく知らせていないと宣言し、「彼はポッドキャストで毎週私を不快にさせる。今日はこちらの番だ」とジョークを飛ばして開幕した。

セッションの骨格は Penn & Teller: Fool Us にインスパイアされた審査形式だ。コミュニティから招いた 4 人のクリエイターがアプリを披露し、「AI スロップ（雑な AI 生成物）」「バイブスコーディング」「AI 拡張ソフトウェアエンジニアリング」の 3 段階のどこに位置するかを Scott と Mark が判定する。ポイントは存在するが重要ではなく、あくまでも楽しみながら AI 開発の実態を炙り出す狙いがある。

セッションの本質は娯楽の裏に込められた問いかけにある。「AI ツールを使えば誰でも良いソフトを作れるのか、それとも根底に専門知識が必要なのか」。4 人の登壇者はそれぞれ極めて異なるアプローチを見せ、結果として「技術的素養なしにバイブスコーディングを本番品質へ昇華させることはできない」という共通結論に収束した。セッション間にはスポンサー（AMD、Intel、NVIDIA、Fireworks AI、Qualcomm）による Karuana Gatimu の取材映像が挟まれ、AI インフラ・エコシステムの最新動向も紹介された。

## チャプター 1: セッション開幕――ルールと三つの判定カテゴリ

Scott Hanselman は Mark Russinovich に今日の内容をまったく知らせていないと宣言し、「彼はポッドキャストで毎週私を不快にさせる。今日はこちらの番だ」とジョークを飛ばした。2 人が設定した判定フレームワークは以下の 3 段階だ。

- **AI スロップ**: AI が無思慮に吐き出した品質の低い成果物
- **バイブス（Vibe Coding）**: 雰囲気に任せた AI コーディング。動くが粗削り
- **AI 拡張ソフトウェアエンジニアリング**: 深い専門知識を持つエンジニアが AI を道具として使い、高品質なものを作るアプローチ

Mark は「コードがどう動くか質問できるんだよな？」と確認し、審査は単なる鑑賞ではなくライブインタビューになると予告した。司会の Scott が「ポイントは意味を持たない」と断りつつも張り合いを演出し、会場の期待を高めた。

## チャプター 2: Steve Sanderson の「vibeOS」――完全幻覚 OS

最初のゲストは Blazor や Knockout.js で知られる Steve Sanderson。彼が披露したのは **vibeOS**――「世界初の完全幻覚 OS」だ。

**デモ内容**: 約 1.3 GB の VHDX ファイルを Hyper-V でブートすると、メモ帳・電卓・Internet Explorer 風 UI が現れる。しかしこれらのアプリにはボタンのロジックもイベントハンドラも存在しない。AI がリアルタイムで HTML を生成し続けることで「動いているように見える」UI を作り出している。

**技術的仕組み**: Steve が説明したアーキテクチャは以下のとおりだ。

1. 最初はビットマップ画像（Stable Diffusion 系）で試みたが、クリック座標の伝達が困難で断念。
2. 次にカスタム DSL や Qt ベースの DSL を試したが精度が出なかった。
3. 最終的に **HTML を DSL として採用**。モデルは大量の HTML を学習済みのため生成精度が高い。
4. 各ウィンドウは独立した iframe。Copilot SDK でセッションを張り、「ユーザーが要素 ID: R1 をクリックした。HTML の差分を出せ」という指示を送り続ける。
5. モデルが差分（diff）を返し、適用することで「偽のステートフル UI」を実現。

デモでは Scott の 1995 年の家計簿（Microsoft Money 95 風 UI）や Mark の Encarta 98 風百科事典、さらに「常に失礼な Commander XE」まで、ユーザーが要求したアプリを即座に「召喚」した。Mark が「OS 内に iOS シミュレータを動かせるか」と問い、ネスト OS が実現されたときには会場が沸いた。

**審査結果**: 所要時間は「数晩、合計 5〜6 時間」と Steve が回答。Scott と Mark は「意図的なスロップを作るために AI 拡張エンジニアリングを駆使した逆説的な作品」と評価し、「バイブスよりも 2〜3 ノッチ AI エンジニアリング側」と判定した。

## チャプター 3: Cassidy Williams の「CSS データベース」――純粋 CSS クエリエンジン

2 人目のゲストは Cassidy Williams（通称 cassidoo）。彼女が披露したのは **純粋 CSS だけで動作するクエリエンジン**をブラウザ内に構築したプロジェクトだ。

**デモ内容**: 一見すると普通の SQL クエリシェル。`SELECT title, cursedness FROM ideas WHERE cursedness = 'Catastrophic'` のようなクエリを入力するとテーブルが絞り込まれ、`DROP TABLE` を実行すると「これは load bearing です（落とせません）」と警告まで出る。さらに本物の SQLite ファイルを WebAssembly 経由でアタッチしてクエリを実行できる。

**種明かし**: 「データベースもクエリエンジンも存在しない。すべて純粋 CSS で実現している」と Cassidy が明かした瞬間、Scott は「Oh no」と声を上げた。実装の核心は以下だ。

- CSS 変数 `sibling-index` を使い行番号・順序を管理。
- `LIMIT` は CSS カウンタと `display: none` の組み合わせで 12 件制限を実装（Scott がコメントし実際に 13 件目を追加してみせた）。
- `ORDER BY ASC/DESC` は **Flexbox の `order` プロパティ**を利用してブラウザエンジンに並び替えを委譲。
- チェックボックスは CSS セレクタで状態を管理し、フィルタ機能を実現。

**制作プロセス**: 約 2 時間、GitHub Copilot アプリと VS Code のサイドチャットを併用。手書きコードの割合は約 20%。「`!important` は使わない。CSS はルールに従って書くべき」と語り、CSS への深い愛着を示した。Mark が「CSS を知らなくてもこのアプリは作れたか？」と問うと、Cassidy は「知らなければ、これをやってはいけないとも分からなかったはず」と答えた。AI は何でも「絶対に正しいです」と肯定するため、誤った方向でも止めてくれなかったとも付け加えた。

**審査結果**: 「バイブスよりも 2〜3 ノッチ AI エンジニアリング寄り」と両名が判定。プロジェクトは Cassidy の GitHub でオープンソース公開済み。

## チャプター 4: Swyx の「AIE Bot」――カンファレンス運営エージェント

3 人目は Swyx（Shawn Wang）。AI Engineer World's Fair の主催者であり、実際に業務で使っているスケジューリングアプリを初公開した。

**背景**: Swyx は年間 3,000〜6,000 人規模のエンジニアリングカンファレンスを運営しており、10 の並行トラックへのセッション割り当てはビン・パッキング問題に近い高精度作業だ。既存の外部 SaaS（民間投資会社が所有し年 20 万ドル相当）では UI のカスタマイズが困難なため、自前でスケジューリングアプリを開発した。

**デモ内容**:

- **Web アプリ**から「Scott Hanselman を Memory トラックに入れて」と自然文で入力すると、エージェントが変更案を提案し承認/却下を促す。人間 in the loop の精度重視設計。
- 同じエージェントを **Slack** 上でも呼び出し可能。`AIE Bot、Mark Russinovich を適切なトラックに追加して` と入力すると、LLM と Web 検索で Mark の経歴（Microsoft SVP）を調べ、適切なトラックを提案する。
- さらに **メール経由**でも同様の指示ができ、返信で確認・承認フローが完結する。「エージェントはあらゆる面に遍在すべき」という思想を実演。

**技術スタック**: Cloudflare（Workers + D1 データベース + Wrangler CLI）、GitHub Actions でデプロイ。エージェントハーネスは「while ループだけ。外部フレームワークは使わない」と Swyx は述べ、ループの反復数に上限を設けて無制限自律を避けている。モデルはミニモデルを採用し速度とコストを最適化。

**種明かし**: コード全体が「完全バイブスコーディング（Gemini による）」だと告白し、会場を驚かせた。「while ループも自分で書いていない。Gemini が書いた」とも打ち明けた。一方で「モノレポ構造でファイルを肥大化させないこと」「並列エージェントで同時編集できる構造を保つこと」については Cursor の指示ファイルを使って意図的に管理していると説明した。

**審査結果**: 「完全バイブスコーディングだが実務で稼働する実用ツール」として高評価。Scott は「音声入力をあえて付けない（OS レイヤーで統一すべき）という判断も AI エンジニアリングの知見」と指摘した。

## チャプター 5: Simon Willison の「Datasette Agent」――8 年間の集大成

最後のゲストは Simon Willison。Hacker News のトップを頻繁に占めるオープンソース開発者で、主要プロジェクトは以下の 3 つだ。

- **Datasette**（8 年間）: データ探索ツール
- **LLM**（3 年間）: コマンドラインおよび Python ライブラリ。主要モデルのプラグインを網羅
- **ブログ**（24 年間）: あらゆる記録が蓄積

**デモ 1 — Datasette Agent（GPT 5.5）**: Postgres の本番ブログを DB2SQLite で SQLite に変換した 100 MB のローカルファイルに対し、「エントリ、引用、ブックマークの件数は？」と自然文で質問。エージェントがテーブルを探索し SQL クエリを実行して「3,000 エントリ、1,000 引用、8,000 ブックマーク」と回答。続いてグラフプラグイン（Datasette Agent Charts）でバーチャートを生成した。

**デモ 2 — Datasette Agent（Qwen3.5、ローカル実行）**: LM Studio 上で動く Qwen3.5 に同じ質問を投げ、完全オフラインで同等の回答が得られることを実証。「ラップトップで動くモデルでも SQL クエリや基本的なツール呼び出しは十分にできる」と述べた。

**デモ 3 — MicroPython サンドボックスプラグイン**: セッション 1.5 時間前に PyPI に公開したばかりのプラグインを紹介。エージェントが WebAssembly サンドボックス内で Python コードを実行できる仕組みで、ホストマシンのファイルを削除するリスクを遮断する。プラグインの構造は `@hookimpl` デコレータを持つ関数と説明リストを返すだけのシンプルな Python コードだ。Datasette 本体は 200 以上、LLM は約 40 のプラグインを持つ。

**AI 活用哲学**:

- **低リスク作業**: 2.5 年前から Claude の Artifacts で自己完結型 HTML ツールを量産（215 本以上を tools.simonwilliston.net に公開）。Claude Code（Web）をスマートフォンから操作し、GitHub Pages に自動デプロイ。
- **高リスク作業（サンドボックス実装）**: コードを厳しく監視。GPT 5.5 にサンドボックス破りを試みさせてエッジケースを洗い出す「敵対的バイブスコーディング」を実施。
- **モデル選択**: 作業の大半は Claude Opus 4.6 を使い、最後にセキュリティレビューとして GPT 5.5 を走らせる。
- 「AI によってプロの開発者の仕事は難しくなった。期待値が上がったから」「以前はバックエンド Python だけに特化していたが、今は Swift UI も書ける（ただし信用するな）」と語った。
- 「複雑なタスクほど AI に任せている間に別のことができる。難易度と集中コストが逆相関になった」という逆説的な変化も指摘した。

**最後のデモ**: 「Simon が最後にペリカンを見たのはいつか？」とエージェントに問い、「今日（6 月 2 日）」と即答。ブログを確認するとその日の投稿にペリカンの観察記録があり、会場が沸いた。

**審査結果**: 全員一致で「AI 拡張ソフトウェアエンジニアリング」と判定。

## チャプター 6: スポンサーセグメント――AI インフラ最前線

セッション合間に Karuana Gatimu が各スポンサーブースを取材した主要ポイントをまとめる。

**AMD（Adrian Macias）**: Microsoft との協業でデベロッパー向けエコシステムを構築。モデル・プラットフォーム・実行場所の選択肢が爆発的に増えた現在、実験コストが実質ゼロになったことで「ハードコミットなしに探索できる環境」が実現したと強調。

**Intel（Bryan Hiestand）**: 30 年に及ぶ Microsoft との協業。CPU・GPU・NPU の「コンピュートコンティニュアム」をまたいだ最適化を支援するソフトウェアツールキットを提供。AIPCs は市場に 1 億台以上。Azure での機密コンピューティングを実現する TDX（Trust Domain Extensions）技術も紹介。

**NVIDIA（Stephen Mccullough）**: ホスト型エージェント Nemotron と Hermes Agent の統合を公開予定（Joey Conway セッションで詳細）。Nemotron はオープンソース高知性モデル、Hermes Agent はオーケストレーション担当として「1-2-3 パンチ」の構成。

**Fireworks AI（Vivek Chauhan）**: 1 日 30 兆トークン処理、企業顧客 1 万社以上。Cursor Composer 2/2.5 にも RL プラットフォームを提供。Azure Foundry との統合により、Foundry のガバナンス・セキュリティ・請求管理を維持しつつオープンウェイトモデルの推論を利用可能に。

**Qualcomm（Ana Schafer）**: デバイス（リング・ペンダント）からデータセンターまで文脈対応エージェントが動く時代への移行を強調。Windows ML、Foundry のファクトリー機能との統合でワークロードを複数フォームファクタにまたいでオーケストレーション。

## チャプター 7: クロージング――バイブスの本質と知識の壁

Scott と Mark は 4 人全員の発表を振り返り、共通する知見を整理した。

**判定の再確認**:

- Steve Sanderson（vibeOS）: AI エンジニアリング寄りのバイブス
- Cassidy Williams（CSS DB）: Mark は「スロップでは？」と言いつつも、CSS 知識がなければ発想不可能と評価
- Swyx（AIE Bot）: 完全バイブスコーディングだが実務で稼働する実用ツール
- Simon Willison（Datasette Agent）: 明確に AI 拡張ソフトウェアエンジニアリング

**核心的な結論**: 「バイブスコーディングは入門ではなく、熟練者の道具だ」。Cassidy は「CSS を知らなければ、やってはいけないことも分からなかった」と述べ、Simon は「AI が期待値を引き上げたことでプロの仕事は難しくなった」と語った。Scott はまとめとして「あなたが何をしているかを理解していれば、必ず成功確率は高まる。何も知らずにバイブスして本番に持っていくことはできない」と締めくくった。

二つの品質保証テクニックへの言及も印象的だった。Mark が紹介した「敵対的バイブスコーディング（一方のモデルが書いたコードをもう一方のモデルが批評し反論させる）」と、Scott が実践する「3 モデル合議リスク分類（全モデルが指摘した問題は高リスク、2 モデルなら中リスク、1 モデルなら低リスク）」。Simon は GPT 5.5 をセキュリティレビューに使う自身の習慣をこの文脈で位置づけた。

## まとめ

### セッション全体の結論

「Scott and Mark Learn to Vibe Check」は、AI ツールがコーディングを民主化したかに見える現在、実際の現場でトップレベルの開発者が何をどこまで AI に委ねているかを生々しく晒したセッションだった。4 人の登壇者は全員が異なる割合で AI を使いつつも、共通して「自分が何を作りたいか・何が正しいかを判断する専門知識」を軸にしていた。バイブスコーディングは正しく使えば強力なプロトタイピング手法になる一方、知識のない人間が同じことをしても品質の保証はできない、というのがこのセッションの最も重要なメッセージだ。

### 技術者向けの次アクション

1. **バイブスコーディングを始める前に領域の基礎を固める**: Cassidy の例が示すように、「何をやってはいけないか」を知っていることが良いバイブスコーディングの前提条件。専門知識が AI のステアリング精度を決める。
2. **プロトタイプは自己完結 HTML で試す**: Simon の tools.simonwilliston.net のように、リスクゼロの静的 HTML ツールとして先にアイデアを形にしてから本番コードに移行する習慣を持つ。
3. **エージェントに無制限の自律を与えない**: Swyx の設計哲学に倣い、LLM ループに最大ターン数を設定し、変更前に人間の承認を挟む「Human in the Loop」アーキテクチャを採用する。
4. **敵対的レビューで品質を担保する**: 重要なコードはメインモデルが書いた後、別モデル（例: GPT 5.5）にセキュリティレビューや攻撃を試みさせてエッジケースを洗い出す。サンドボックス実装のような高リスク箇所では特に有効。
5. **エージェントを複数のサーフェスに展開する**: Swyx が示したように、Web UI・Slack・メールを横断してエージェントを使えるようにすることで、既存のワークフローを壊さず AI の恩恵を受けられる。Cloudflare + GitHub Actions のような軽量スタックでも実現可能。
