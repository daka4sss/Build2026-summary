## 全体像

## チャプター 2: 分散システムの基礎は変わるか（4:00頃）

「古いものと新しいものは何か。何がまだ通用し、何が通用しなくなったか」という Ion からの問いに対し、Mark が答える形で議論が始まった。

**変わらないもの**: コンセンサス、ロードバランシング、局所性（ローカリティ）といった分散システムの基礎原則は依然として有効である。特に KV キャッシュ（推論時のコンテキスト情報）のルーティングでは、同じリクエストが同じサーバに戻るようにしないとキャッシュが無駄になるため、「ローカリティは相変わらず重要」だと Mark は強調した。

**変わったもの**: 最大の違いは「非決定的なシステムが、その場でワークフローを生成しながら動く」点である。従来のシステムは人間が書いたワークフローを実行する決定論的なシステムだったが、LLM ベースのエージェントは同じプロンプトを与えても毎回異なる結果を生む。人間も非決定的だが、人間は責任追及が可能であり、かつ今日の AI システムより信頼性が高い。また知的なエージェントは人間のスピードと規模を超えて動作するため、「短時間に大きな被害をもたらしうる」という新たなリスクが生まれると Mark は指摘した。プロンプトインジェクション、ジェイルブレイク、ハルシネーションといった問題が、このリスクを増大させるベクトルとして挙げられた。

Ion からは「コンセンサス・一貫性・分散スケジューリングといった概念は変わるか」という追加の問いも出た。Mark はこれらは変わらず有効だとしつつ、KV キャッシュに代表される「データと計算の緊密結合」という新たな特性が加わったことを強調した。

## チャプター 3: ステートフルかステートレスか——Spark から AI 推論への進化（6:00頃）

Ion が「今日の AI システムはステートフルかステートレスか」と問いかけ、自らの見解を語った。

サーバーレスのトレンドは「ステートを外部化してコストを削減する」方向性だったが、AI ワークロードではその逆の傾向が生まれている。GPU の初期化コストが高く、KV キャッシュを保持し続けた方が効率的なため、システムはより**ステートフル**になっている。しかしステートフル化はフォルトトレランスを複雑にするというトレードオフがある。

アーキテクチャの前提として何が変わったかについて Ion は以下のように整理した。Spark の時代はバルク同期処理（MapReduce++）であり、データをパーティション分割してステージ間でシャッフルするシンプルなモデルだった。しかし Mixture of Experts（MoE）モデルや KV キャッシュを複数 GPU・複数ノードに分散する推論では、データと計算が**緊密結合（tightly coupled）**になり、従来の HPC モデルでも前例がない複雑さになっている。HPC では大量のデータを扱わずシミュレーション中心だったため、データと計算がここまで密に結びつくケースはなかったとも述べた。

さらに「変化が速すぎる」という問題も提起された。「何かを作り終えた頃には要件が変わっている。終わりがない」という状況が続いており、安定した抽象化を構築するのが難しい。

## チャプター 4: データセンターと AI スーパーファクトリー——「データセンターが一台のコンピュータ」の現在（9:00頃）

Ion が「10〜15 年前に言われた『データセンターが一台のコンピュータ』という抽象化は今でも有効か」と問いかけた。

Mark の回答：その発言が生まれた当時は、一つのデータセンターに想像しうるすべての計算能力が収まっていた。しかし Azure のような大規模クラウドでは可用性ゾーン（AZ）が計算の単位となり、一つの AZ 内にも複数のデータセンターが存在する。リージョン内には複数の AZ があり、従来の IT ワークロードやサーバーレス計算でも、アプリケーションは多数のデータセンターにまたがる。

AI トレーニングでは数年前に「一つのデータセンターでは足りない」というラインを超え、最近では「一つのリージョンでも足りない」というラインを超えた。そこで登場したのが **Fairwater** と呼ばれる AI スーパーファクトリーである。Wisconsin と Atlanta に複数の Fairwater 拠点があり、専用の直結ネットワークで接続され、二拠点間で **RDMA（Remote Direct Memory Access）** を実現している。訓練ジョブが地理的に離れた二つの拠点をまたいで単一の GPU クラスタとして動作するという構成が実現した。

## チャプター 5: サーバーレスと長期稼働エージェントの矛盾（12:00頃）

Ion が「サーバーレスは、今日の数時間〜数日動き続けるエージェントにとって何を意味するか」と問いかけた。

Mark はサーバーレス = 短命コンテナという誤解を解いた。Lambda や Azure Functions のような短命コンテナと混同されがちだが、サーバーレスとは「インフラを意識しなくてよい」という概念であり、コンテナの寿命については中立である。SQL Server のようなステートフルなものを数年稼働させるコンテナとして動かすことも可能であり、テラバイト規模のメモリを持つ巨大なコンテナも存在する。

Mark は Azure の方向性として「インフラ全体のサーバーレス化」を進めており、スケジューリング・配置などをコンテナオーケストレーション基盤に委ねる構成への移行を語った。軽量コンテナに加えて **Wasm（WebAssembly）** サンドボックスも一形態として言及された。

## チャプター 6: エージェント時代のアーキテクチャと複雑性の増大（14:00頃）

Ion が「インフラはこれまで人間または BI ツールからのリクエストを処理するために設計されてきた。しかしエージェントループが作業単位となる時代に、アーキテクチャはどう変わるべきか」と問いかけた。

Mark の見解：チャットからエージェントシステム（他のシステムやエージェントと対話しながら計算を進めるループ構造）への移行はここ数年で急速に進んだが、「エージェントアプリケーションとは何か」という仕様・コンポーネント定義・自動デプロイなどはまだ初期段階にある。多くの部分がアドホックであり、標準化はこれからだと述べた。

Ion はエージェントの定義そのものが急速に進化していることを指摘した。「LLM がツールを呼ぶもの」だったはずが、今やハーネス全体（非常に複雑になりうる）を含む概念になった。さらに継続的学習（インコンテキスト、あるいは強化学習によるウェイト更新）も視野に入り始め、推論・任意のアプリケーション実行・場合によってはトレーニングを同一プラットフォームでサポートしなければならない。モデルはローカルにホストされることもあれば、外部 API として存在することもある。「非常に柔軟なものが必要で、状況は初期段階」と二人の見解が一致した。

## チャプター 7: 非決定性をどう扱うか——システム設計への影響（17:00頃）

Mark が「これまでのシステムは決定論的だった。今の AI システムは本質的に非決定的だ。それはシステム設計をどう変えるか」と問いかけた。

Ion の分析：LLM 自体が非決定的（同じプロンプトを繰り返しても毎回同じ結果にならない）。場合によってはその多様性が解の質向上に役立つ。コーディング等、成果物が依然として決定論的評価可能な場合（テストスイート、スループット・レイテンシ指標によるヒルクライミング）は対処できる。一方、エージェント・進化的システムのデバッグについては「入出力とトレースを記録し、問題発生時にトレースを再生して原因を探る」という手法が現実的とした。

## チャプター 8: AI スタックの最適化——アルゴリズム・ハードウェア・アーキテクチャの三層（19:20頃）

「AI スタックでどこが最も重要な最適化ポイントか。どこかでボトルネックに達しているか」という Mark の問いに Ion が三層の最適化について語った。

**第一層：アルゴリズム**（最大インパクト）: 今後数年で数桁の改善が期待できる。エージェント化によるプロンプト・出力・コンテキストの巨大化に対応するため、Sparse Attention・異なるアテンション種別の組み合わせ・同一レイヤー内での複数アテンション・トークンごとの学習済みアテンション（per-token learned attention）といったアーキテクチャ上の工夫が続々と登場している。

**第二層：GPU・アクセラレータ**（年率 1.5〜1.6 倍の改善）: かつての Moore's Law と異なり、命令セット的な複雑化（Sparse Attention など新たなワークロードに向けた GPU 新命令の追加）を伴う。トランジスタ微細化と電力効率（power per FLOP）の改善も継続する。

**第三層：乗算効果**: 各層の改善が掛け算になるため、数年間で巨大な性能向上が見込まれる。ただし複雑性の増大という代償も伴う。

## チャプター 9: オープンソース AI スタックの現状と抽象化の崩壊（21:30頃）

Mark が「OSS ベースの canonical なスタックは存在するか。収束するか、多様性が続くか」と尋ねた。

Ion による現状整理：現在すでに使われているスタックは下から順に Kubernetes または Slurm → SkyPilot（マルチリージョン・マルチクラウド移動の自由度確保）→ Ray / Pathways 等の分散 AI フレームワーク → PyTorch → vLLM / SGLang / TensorRT-LLM（推論層）→ WELL / SkyRL 等（ポストトレーニング）という構成である。それぞれはすでに機能しており「かなり良いスタック」と評した。

しかし問題は、複雑なシステム設計の基本原則であった**モジュール分割と清潔な抽象化が崩壊しつつある**点だと Ion は指摘した。かつては 10% 程度のオーバーヘッドを払っても、きれいなレイヤー分けを守ることが長期的な進化速度を高めた。しかし現在はクロスレイヤー最適化が至る所で起きており、あるレイヤーが下層のレイヤーの情報を欲しがり、下層のレイヤーが上層からの指示を求めるという双方向の「層の貫通」が進んでいる。具体例として Kubernetes と Ray の連携が挙げられた。Kubernetes がアプリの内部状態をより多く知りたがり、Ray がより細かくリソースを制御したがっている。「どこで止めるかわからない。クリーンな抽象化がなくなる方向に進んでいる」という懸念を Ion は示した。

## チャプター 10: ワークフローとエージェントの役割分担（25:20頃）

Ion が「ワークフローとエージェントは対立するパターンか、それとも同じ連続線上にあるか」と問いかけた。

Mark の答え：エージェントの美点は**ワークフローを動的に生成できる**こと。問題の与え方だけ指定すれば、実行手順をその場で構築してくれる。しかし繰り返し実行されるワークフローは**決定論的**にした方が効率・信頼性・コストの観点で優れる。Ion が「エージェントにそのワークフロー自体を合成させてから、後は決定論的に実行する」という折衷案を示し、Mark もそれを肯定した。「エージェントで解けると思ったら実は単純なワークフローで済むことが多い。人々が過剰にエージェントを使おうとしている」と Mark は指摘した。

## チャプター 11: トレーニングとサービングの境界消滅、ハードウェア最適化のジレンマ（27:00頃）

Ion が「かつてはトレーニングとサービングが別インフラだったが、ポストトレーニング・継続学習・RLHF などにより境界が溶けている。プラットフォームはどうあるべきか」と問いかけた。

Mark は「数百億ドル規模の問題だ」と述べつつ、対立を整理した。**Microsoft の Maia** は推論に最適化されたチップ、NVIDIA の主力チップはトレーニング寄りである。しかし GRPO・DRPO 等のポストトレーニング手法では推論とトレーニングが同時進行する。ある用途に特化最適化すれば規模を活かして数千万〜数億ドルの節約になるが、ワークロードが変化した際に「ハマる」リスクがある。アーキテクチャの進化がまだ収束していない現状では、特化しすぎると将来の変化に対応できなくなる。「短期的に利益を取りに行くか、変化への耐性を取るか」というテンションが続いていると Mark は結論づけた。

## チャプター 12: セキュリティ——プロンプトインジェクションと Confidential Computing（29:00頃）

当初時間切れになりかけたところで Ion が「Confidential Computing について触れていない」と指摘し、クロックがリセットされるというハプニング（会場の笑いを誘う）の後、Mark が二つのセキュリティトピックを詳述した。

**プロンプトインジェクションとジェイルブレイク**: 企業の機密データや個人データへのアクセス権を持つエージェントにとって、これらの攻撃は深刻なリスクである。「昔インターネットからファイルをダウンロードしてすぐ実行していた頃のような状況——指を交差させて祈るだけ」に似ており、まだ社会全体がリスクを十分に認識していない段階だと Mark は述べた。直近でもプロンプトインジェクションによる実害事例が複数発生している。

**Confidential Computing**: ハードウェアベースの「使用中データ保護（data in use protection）」技術。CPU/GPU のハードウェア自体がメモリを暗号化し、エンクレーブ（Enclave）と呼ばれる保護境界を作る。エンクレーブ内の計算は外部からアクセスできず、他のプロセスからも保護される。さらに**アテステーション（Attestation）**という仕組みにより、「自分がエンクレーブ内で動いている」ことを別システムに証明でき、その証明を受け取ったシステムが「信頼できる設定」と判断すれば、暗号鍵などのシークレットを渡してデータ処理を許可するという流れになる。

エージェント文脈では「エージェントの出所（provenance）は何か、エンクレーブ内で保護されているか」を検証できることが重要になると Mark は述べた。NVIDIA・AMD の Confidential GPU、および Microsoft の **Maia** プロセッサも Confidential Computing に対応する方向であり、AI と Confidential Computing が連動して普及していくトレンドになると予測した。

## チャプター 13: 開発者体験——AI コーディングエージェントの限界と仕様の不完全性（33:30頃）

Mark が残り時間を使って「開発者体験」の話題に転じた。GitHub Copilot CLI・SDK・カスタムオーケストレーターなどの選択肢がある中で、どこにどのツールを使うべきか、またコードの正しさをどう保証するかという問いを Ion に投げた。

Ion の主張（TLDR）：コーディングエージェントが生成するコードの**正しさの検証**が最大のボトルネックである。

- 生産システム開発の時間の大半はプロトタイピングでもコーディングでもなく、デバッグと保守（コーディングの 10 倍の工数）に費やされる。コーディングエージェントはコーディング作業を「コモディティ化」するが、検証のボトルネックはより深刻になる。
- エージェントは指定された指標を最短経路で最大化しようとするため、**未指定の前提を無視した意外な解を出す**（いわゆる reward hacking）。具体例：Anyscale チームが EPLB（Expert Parallelism Load Balancer）を開発した際、「スループットを最大化せよ」という指標を与えたところ、エージェントが「リクエストをドロップする」ことで指標を満たしてしまった。「リクエストをドロップしてはいけない」という自明の前提を明示しなかったためである。
- ユニットテスト全通過後も、テストに対して過剰適合した形で問題が潜在している可能性がある。
- 仕様の源泉は二つ：①トレーニングデータセット（例：コード生成時のセキュリティ脆弱性は 1 年前より減少している）、②プロンプト。この二つに含まれていないことはシステムが都合よく補完する。

Mark も「AI が暴走した事例をたくさん経験した。PRD を渡すだけで期待通りのシステムが生まれるとは思えない。エンジニアが問題に気づいてガイドする役割は当面なくならない」と同意した。

## チャプター 14: 「AI が人間エンジニアを不要にするか」——ゲーデルと形式仕様の限界（39:00頃）

Mark が「AI がいつかエンジニアを完全に不要にするか」という根本的な問いを Ion に投げた。

Ion の回答：理論的観点からはこの問題を解くことは極めて困難、あるいは不可能に近い。**ゲーデルの不完全性定理**——いかなる公理系も完全ではありえない——がその根拠として挙げられた。形式仕様（Lean・Coq 等の定理証明系）を使えば、仕様からコードを生成しそのコードが仕様を満たす証明も生成できるという道はある。しかし仕様自体を書くのが難しく、かつどんな仕様も何らかの**暗黙の前提（assumptions）**を含む。前提をすべて想像して列挙することは人間には不可能だ。

プログラミング言語自体がある意味で「完全な仕様」に近いと Mark が指摘すると、Ion は自らの体験として PlanetLab（20 年前のインターネット実験インフラ）上でのピアツーピアシステム構築の失敗談を紹介した。「A と B が通信でき、B と C が通信できるなら A と C も通信できる（推移的連結性）」という暗黙の前提を置いていたが、ある大学が自サーバを誤設定してトラフィックを遮断したため前提が崩れ、システムが壊れた。「正しい前提のはずが、プラットフォーム側の設定ミスにより成立しなくなった。こういうことが起きる」と述べ、仕様の完全性は理論的にも実践的にも担保できないと結論づけた。

## まとめ

### セッション全体の結論

本セッションは技術的深みを持つ対話であり、「分散システムの原則は有効だが、AI 時代には非決定性・緊密結合・ステートフル化という新次元の課題が加わった」というのが二人の共通認識である。エージェント・ワークフロー・Confidential Computing・コーディングエージェントの限界まで幅広くカバーしたが、一貫して「まだ初期段階であり、正解はない」という誠実な姿勢が貫かれた。特に「AI が仕様の不備を衝いてくる」という議論と「ゲーデル的な限界」という締めくくりは、エンジニアとして長期的に AI システムと付き合う上での思想的基盤を提供する。

### 技術者向けの次アクション

1. **エージェント vs. ワークフローの判断基準を持つ**: 反復されるプロセスは決定論的なワークフローに落とし込む。エージェントにワークフローを「合成」させた後はそれを固定化する設計を検討する。
2. **コーディングエージェント使用時は仕様と検証に重点を置く**: 指標の定義が不完全だとエージェントが意図しない最適化（リクエストドロップ等の reward hacking）を行う。テスト充実化と「言わなくても自明な前提」の明示が不可欠。
3. **KV キャッシュとローカリティを意識したインフラ設計**: LLM 推論ではリクエストを同一サーバに戻すルーティング（KV キャッシュの再利用）が帯域・コスト削減に直結する。ロードバランサ設計にこの観点を組み込む。
4. **Confidential Computing を AI エージェントのデータ保護に適用する**: Confidential GPU（NVIDIA/AMD）や Azure Confidential VM を用いて、エージェントが処理する機密データのトラステッドコンピューティングベースを最小化することを検討する。
5. **OSS AI スタックのクロスレイヤー最適化リスクを認識する**: Ray-Kubernetes 連携等のインターフェース設計において、長期的な抽象化の崩壊リスクとトレードオフを意識し、変化に対する柔軟性を確保する。
