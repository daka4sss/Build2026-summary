## 全体像

本セッションは、エンタープライズ向けに「どのエージェントフレームワークで作っても」セキュリティ・ガバナンス・オブザーバビリティを後付けではなく最初から組み込める手段として、**Agent 365 SDK** を紹介するものである。前半はインタビュー形式でエンタープライズが抱える不安を整理し、後半はライブデモで Microsoft Entra・Purview・Defender との統合を実際の画面を通じて示した。

Agent 365 は 2026 年 5 月 1 日に **GA（一般提供開始）** となっており、SDK と合わせて提供されている。OpenAI SDK / LangChain / Claude / LlamaIndex / Microsoft Agent Framework / カスタムコードなど、既存のいかなるフレームワークとも組み合わせ可能な「差し込み型」の設計が最大の特徴である。

全体を通じたメッセージは「エンタープライズが承認するエージェントとは、最も派手なエージェントではなく、CISO が本番展開を認めるエージェントだ」というものであり、開発者に対してセキュリティを後回しにしないよう強く訴えた。

## チャプター 1: エンタープライズが夜眠れない理由 — 4 つのリスク（0:00頃）

Sunil Garg はまず、エンタープライズが抱える不安を 4 つに整理した。

### 1. エージェントスプロールとリソースアクセス

82% のリーダーが今後 12〜18 か月以内にエージェントをデプロイする計画を持っている。しかし各チームが独自にエージェントを立ち上げると、それぞれがアイデンティティ・権限・データ・ツールへのアクセスを必要とする。

**重要なメンタルモデルの転換**：「エージェントはアプリではなく、自分の頭脳を持つ**アクター**である」。スコープされたアイデンティティ、最小権限アクセス、監査証跡を最初から設計すること。ガバナンスを後から追加しようとすると手遅れになる。

### 2. データの過剰共有（Data Oversharing）

80% のリーダーが「AIを通じた機密データ漏洩」を最大の懸念として挙げている。これはモデルの問題ではなく、**グラウンディングの問題**である。エージェントが SharePoint・CRM・メールスレッドにアクセスできても、それをこのコンテキストで表面化すべきかどうかは別問題だ。開発者はデータ境界・センシティビティラベル・ユーザー委任権限を意識した設計が必要である。エージェントを既存のエンタープライズ制御を迂回するショートカットにしてはならない。

### 3. 新たな脅威面 — 間接プロンプトインジェクション

88% の組織が間接プロンプトインジェクションを懸念している。エージェントがメールを読んだり、ドキュメントを解析したり、ウェブページをブラウズした瞬間に、信頼できないコンテンツがその推論ループに入り込む。開発者はエンタープライズのセキュリティチームが検知・対応できるようなフックとガードレールをエージェントに組み込む必要がある。Microsoft Defender がここで機能する。「エージェントは必ず操作される」と仮定し、グレースフルフェイルを設計すること。

### 4. 規制の不確実性

リーダーの半数以上が AI の規制を完全には理解していないと認める。EU の金融・ヘルスケア向けセクター別ルール、米国のガイダンスも発展途上だ。Sunil のアドバイスは「ルールが固まるのを待つな。今すぐオブザーバビリティとトレーサビリティを構築せよ」。「このエージェントは、誰の代わりに、何のデータを使って、何をしたか」という問いに答えられれば、どんなフレームワークにも対応できる。

**結論**：企業が恐れているのは 1 つのリスクではなく、「アクセスが多すぎるエージェントが、信頼できないデータ上で推論し、誰も監査できない意思決定を、まだ書かれていない規制環境の中で行う」という複合リスクである。

## チャプター 2: 「エージェントは従業員」という発想転換 — エンタープライズが問う 4 つの質問（5:36頃）

Sunil はエージェントを「アプリケーション内の機能」ではなく「**ワークフォースのメンバー**」として捉えるべきだと説明した。

新入社員が入社するとき、IT はマネージドアイデンティティをプロビジョニングし、アクセスはロールに限定され、上司が期待値を設定し、すべての行動が監査可能になる。エージェントも同じ扱いが必要である。

エンタープライズ顧客がエージェントについて問う質問は、新入社員について問う質問とほぼ 1:1 で対応する：

1. **「IT は発見・管理できるか？」** — 現時点では大半の場合 No。最初からアイデンティティを付けて登録すること。IT が見えないものは、IT が守れない。

2. **「誰と機密情報を共有しているか？」** — 個々の権限ではなく、データのフローで考える。CRM からの読み取りとメール送信という 2 つの権限は単独では問題がなくても、組み合わせると情報持ち出しパスになりえる。個別アクションではなく全体フローを設計すること。

3. **「適切に振る舞っているか？」** — テレメトリ・行動シグナル・フックを組み込み、エンタープライズのセキュリティチームが監視・修正できるようにすること。見えないものは直せない。

4. **「適切にガバナンスされ監査されているか？」** — すべてのアクションが「どのエージェントが、誰の代わりに、どのデータを使って、どんな結果を出したか」という形で帰属可能でなければならない。

**開発者へのガイダンス**：エンタープライズ対応エージェントの基準は「動くかどうか」ではなく、「Fortune 500 のオンボーディングレビューを通過できるか」である。アイデンティティ・行動・データ扱い・監査可能性、この 4 つを満たして初めて「信頼されるエージェント」になる。信頼こそがデモを本番に変えるものだ。

## チャプター 3: Agent 365 SDK の概要 — フレームワーク非依存のインクリメンタル統合（8:39頃）

Jeremiah が「開発者が自分でセキュリティスタックを再構築せずにその基準を満たすにはどうすればよいか」と問うたのに対し、Sunil が Agent 365 SDK の設計思想を説明した。

### 問題の背景

開発者がエンタープライズ対応エージェントを構築するのは現状では困難だ。オープンソースや開発ツールを組み合わせ、コントロールを自分で正当化・特定・パッチ適用しなければならない。複数ベンダーのコントロールを維持してエンタープライズ対応にするのは難しい。

### Agent 365 とは

Agent 365 はエージェントのコントロールプレーンであり、エンタープライズ顧客がすべてのエージェントを**観察（observe）・管理（govern）・保護（secure）**できるように設計されている。2026 年 5 月 1 日に **GA（一般提供開始）** となった。

### Agent 365 SDK の 3 つの柱

**Agent 365 SDK はオール・オア・ナッシングではない。** OpenAI SDK / LangChain / Claude / LlamaIndex / Microsoft Agent Framework / フルカスタムコードのいずれで構築していても、インクリメンタルに Agent 365 の機能を重ねることができる。

#### 1. オブザーバビリティ（Observability）

SDK は **OpenTelemetry** ベースの完全なトレーシングを追加する。すべての入力・出力・ツールコール・モデル起動が記録される。

開発者には 2 つのパスがある：

- **Microsoft OpenTelemetry Distro**（推奨）: OpenAI・LangChain・Agent Framework の自動インストルメンテーションが付属し、その他のすべてに対するフックも含む。
- **OTel エンドポイントへの直接注入**: すでに OpenTelemetry パイプラインが稼働している場合や、SDK がまだ対応していないスタック（Java など）の場合に使用できる。既存資産を再利用可能。

さらに、コーディングエージェント向けの **AI ガイド付きセットアップ** が用意されており、登録とテレメトリを自動的にワイヤアップしてくれる。開発者がドキュメントを読み込んで最初のトレースに到達するまでの手間を省く。

オブザーバビリティが有効になると、エンタープライズのセキュリティチームは Microsoft Defender ポータルで**脅威ハンティング**に活用できる。統合オブザーバビリティ SDK により IT チームとセキュリティチームの双方が完全な可視性を持ってエージェントを保護・管理できるようになる。

#### 2. ガバナンス（Governance）

Agent 365 SDK により、顧客の IT・セキュリティチームがツールアクセスを管理できるようになる。**MCP（Model Context Protocol）** を通じた Microsoft 365 データへのアクセス（メール・カレンダー・OneDrive・SharePoint・Teams）は、管理者が制御・監査・取り消し可能なガバナンス済み権限として提供される。

開発者がコネクタを独自構築したり、コンセントフローを自前実装する必要はない。SDK がツールサーフェスを提供し、管理者がエージェントに何を触らせるかを決める。開発者が独自の MCP を持ち込んで Agent 365 に登録することも可能で、その場合も同じ制御下のアクセスが得られる。

#### 3. セキュリティ（Security）

**Entra Agent ID** がここで機能する。SDK を通じて Entra Agent ID を有効化すると、顧客の管理者に対してアイデンティティ保護・条件付きアクセス・ID ガバナンスといった一連の機能がライトアップされる。エージェントは実在する検証可能なアイデンティティを得て、管理者はユーザーと同じ Entra コントロールで管理できる。

**要約**：使いたいフレームワークやモデルを持ち込めば、Agent 365 SDK がオブザーバビリティ・ガバナンス・セキュリティをインクリメンタルに付与する。リライトは不要。

## チャプター 4: Entra・Purview との統合詳細（16:07頃）

Jeremiah の「SDK 統合後に Entra と Purview はどう機能するか」という問いに対し、Sunil が整理した。

### Entra Agent ID

Entra Agent ID は Agent 365 SDK の一部として含まれている。SDK と統合した時点で、アイデンティティとアクセス管理・ガバナンス・Defender での脅威ハンティングがすべて自動的にライトアップされる。追加配線は不要。

### Microsoft Purview

データセキュリティとコンプライアンスのコントロール（センシティビティラベル・DLP・データライフサイクルポリシー）は、エージェントがユーザーとインタラクションする M365 サーフェス（Teams など）上で機能する。

Microsoft は開発者が利用できる **Purview API** も提供しており、これを使えば他のシナリオのエージェントにもデータコントロールを組み込める。エンタープライズ顧客は自身の Purview ポリシーを設定・適用してランタイムに機能させることができる。「さらに開発者にとって使いやすくしていく予定」（Sunil 発言）。

統合パターン：同じエージェントに対して 2 つの拡張パス — 「ビルトイン（M365 上の自動適用）」と「ランタイムフック（Purview API 利用）」。

## チャプター 5: ライブデモ — Genspark エージェントによる統合実証（17:44頃）

Sunil が Genspark のエージェント（Agent 365 SDK 統合済み）を使って、エンタープライズ顧客が受け取るセキュリティアウトカムを実際の画面で示した。

### デモ 1: Microsoft 365 Admin Center でのエージェント可視化

Genspark はすでに Agent 365 SDK と統合済みであるため、エージェントは Entra Agent ID と**ブループリント**を持っている。その結果、Microsoft 365 Admin Center にエージェントが表示され、他のエンタープライズ資産と同様に「可視・目録化・管理可能」な状態になっている。

ブループリントによる登録が完了した瞬間、エージェントはテナント内で **Microsoft Entra Agent ID**（ファーストクラスのアイデンティティ）を取得する。これにより：
- 組織がすでに人間ユーザーに対して行っているガバナンスと同じガバナンスが自動的に適用される
- エージェントの監査ログを確認できる
- エージェントがアクセス試行したエンドポイントのサインインログを確認できる
- 人間ユーザーと同様にエージェントを監査できる

### デモ 2: Purview によるデータ制御

センシティビティラベルの適用デモ。「Highly Confidential」ラベルが付いたドキュメントを「人間ユーザーのみに共有」と設定した場合、そのドキュメントをエージェント自身が作成したものであっても、エージェントはそのドキュメントを読めないようブロックされることを示した。

続いて DLP（データ損失防止）ルールのデモ。「ユーザーが AI エージェントと機密データを共有することを禁止する」という DLP ルールを設定すると、Purview がそのメッセージをブロックした。Purview はプラットフォームレイヤーで強制適用される。「人間を守る同じコントロールが、今やエージェントを守る」（Sunil 発言）。

### デモ 3: Defender による継続的な脅威検知

Defender はエージェントの行動を継続的に監視する。異常なツールコール・異常なデータアクセスパターン・侵害の兆候を検知する。

**プロンプトインジェクション攻撃への対応デモ**：ユーザーがプロンプトインジェクション攻撃を試みたところ、高重要度アラートが発生し、ルールが起動してツールがブロックされた。

この機能は Agent 365 上で利用可能なすべてのツール（MCP を含む）に対して機能し、独自の MCP を Agent 365 に登録した場合も同様に機能する。

**結論**：何か問題が起きたとき、セキュリティチームは AI エージェント専用のカスタムプレイブックを必要としない。既存のプレイブックをそのまま使える。

## まとめ

### セッションの結論

Jeremiah によるまとめ：エンタープライズ顧客が必要としているのは「エージェントスプロールの管理・データ漏洩防止・脅威からの保護・コンプライアンス要件の充足」である。Agent 365 はこの基準をすべてのエージェントで満たすための手段であり、Microsoft AI プラットフォームで構築したエージェントにも、Agent 365 SDK を通じて外部で構築したエージェントにも対応する。

Sunil の最後のコメント：「高速にシップすることとエンタープライズ対応であることを選択する必要はない。SDK を使えば、今使っているフレームワークで構築し続け、SDK を統合した瞬間にエンタープライズ顧客が期待するアイデンティティ・ガバナンス・セキュリティ機能を引き継げる。それが採用を解き放つものだ」。
