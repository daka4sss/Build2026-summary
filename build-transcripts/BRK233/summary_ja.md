## 全体像

Chip Huyen は「自分が得意だったこと（ライティングとコーディング）がまさに AI に最も自動化されやすい領域だ」という個人的な危機感をきっかけに、このセッションを構成している。AI コーディングが急速に進化する中で、「いかにソフトウェアを守るか（Software Defensibility）」という問いを中心に、競合優位性（モート）の変質、AI 時代に残る本当の問題空間、そして物理 AI エージェントとロボティクスまで、幅広い視点で論じる。

会場には多数のソフトウェアエンジニアが参加しており、随所で聴衆への質問を投げかけながら双方向的に進む形式のセッションである。プレゼンテーションは「ソフトウェアのコスト接近ゼロ」→「モートの無効化」→「残る問題領域の探索」→「AI エージェントの進化」という構造で展開された。

AI が生成するコードの品質と量が急上昇する現在、問題の本質は「どう作るか」から「何を作るべきか、そして作ったものをどう守るか」へと移行している。最終的には、AI 時代においても新たな問題は絶えず生まれ、特にロボティクスや物理エージェントという新フロンティアに大きなチャンスがあると締めくくる。

## チャプター2: ソフトウェアのコストはゼロに近づいているのか？（1:48頃）

AI によりソフトウェア開発コストが急速に低下しているという議論を展開した。具体的には、かつて A/B テストで 10〜20 バリエーションしか作れなかった会社が、今では AI を使って 1,000 バリエーションを容易に生成できるようになっているという事例を挙げた。

ここで重要な問いを立てる：「コストがゼロに近づくなら、価値もゼロに近づくのか？」

**Claude Code を使ったコピー体験談（印象的なエピソード）**

Chip は週末プロジェクトとして副業サービスを立ち上げ、1週末で 30 万 PV を獲得した。しかし翌日、見知らぬ人物からメールが届き、「あなたのアイデアが好きだったので Claude Code にそのまま作らせました。URL はこちらです」と告げられた。「嬉しいような、腹立たしいような複雑な気持ちになった」と述べた。

このエピソードが示すのは、「今存在するいかなるソフトウェアも容易に複製できる」という現実だ。Airtable も Asana も、AI に頼めばビルドできる。さらに Chip は「killbygpt.com」（AI に最初に殺される製品に投票するサイト）を翌週ローンチ予定だと言い、「みなさんも Claude Code で複製できます」と笑いを取った。

また、METR（M-E-T-R）の AI 自動化研究を引用した。METR のベンチマークは「AI が 50% の確率で確実に完了できるタスクの長さ」を計測しており、初期は数秒規模だったが今では 16 時間規模のタスクを完了できるようになっている（対数スケールのグラフを線形スケールで見れば指数関数的な成長）。「AI がいずれ Google レベルのものも作れるようになるかもしれない」と述べた。

「ソフトウェアの Ghibli モーメント」という比喩も登場した。OpenAI でジブリ風画像が生成された際、アーティストたちは「自分が何年もかけて築いたスタイルを一瞬で模倣される」と怒った。同様に、ソフトウェアも「既存製品の名前を言うだけで AI が作れる」という構造になっており、「製品をリリースすること自体が競合他社への仕様書の提供になってしまう」と述べた。

**結論**: AI 時代においては「どう作るか」はもはや主要問題ではない。「何を作るか」と「それをどう守るか」が本質的な問題となった。

## チャプター3: 従来のモート（競合優位性）はもはや有効か？（6:27頃）

聴衆に「あなたのプロダクトのモートは何か？」と問いかけ、回答として「プロプライエタリデータ」「信頼・ブランド」「カスタマーサービス」「ディストリビューション（流通）」「専門性（エキスパーティーズ）」などが挙がった。それぞれを Chip が順に考察した。

**データはモートか？**

かつてはデータ独占が参入障壁だと信じていたが、大手 AI フロンティアラボが資金力でデータを購入・取得している現状を指摘した。QuickBooks の例：「QuickBooks が OpenAI にデータを売らなくても、OpenAI が Scale AI（データラベリング会社）などに依頼して 1万人の会計士を雇い、QuickBooks 相当のワークフローデータを生成できる」。データラベリング会社が年間数十億ドルの売上を記録するのはそのためだ。「データはもはやモートではなく、カネがモートだ」と総括した。

**ブランド・信頼はモートか？**

信頼は重要だが、AI モデルの改善ペースが速すぎて顧客ロイヤルティを上回る可能性がある。ChatGPT 登場後、Claude/Anthropic、DeepSeek、Qwen と次々に人々が乗り換えていった例を挙げた。

**ディストリビューション（流通）はモートか？**

エンタープライズ向けには一定の有効性がある。ただし「流通もカネで買える」という課題がある。例として、ある VC パートナーが工場向けソフトウェア会社（非 AI 系）を買収することで、一気に 1万社の顧客を手に入れたケースを紹介した。「AI 会社は資金力があるので、既存の流通チャンネルごとソフトウェア会社を買収できる」と指摘した。また、ディストリビューションをモートにする戦略は「顧客の不満・不便さに依存する」という側面があり、倫理的・持続可能性の問題も孕むと述べた。

**専門性（エキスパーティーズ）はモートか？**

専門性はスケールするためにはソフトウェアにエンコードする必要があるが、そうすると「ソフトウェア化された専門性は複製可能」になるというジレンマがある。

**モメンタム（速度）だけが残るモートか？**

「競合より速く動き続けること」が唯一のモートかもしれないが、それは「終わりなきトレッドミル」に乗り続けることを意味し、プレッシャーが非常に高い。投資した会社が 0→10M ARR は達成できても 100M ARR に届かず IPO 困難という状況を目撃してきたとも述べた。

## チャプター4: 残る問題空間 ― ロングテール問題と新たな機会（13:07頃）

「AI がどれだけ良くなっても、常に解くべき問題は存在する」という信念を表明した。AI が進化することで解決できる問題もあるが、同時に新たな問題が生まれる。ここでは「ロングテール問題」の重要性を論じた。

**ロングテール問題の定義**

フロンティア AI ラボは人口の 99% が持つ問題（汎用ライティング、コーディング支援、英語対応など）に注力する。しかし、人口の 1% しか持たない固有の問題は AI ラボにとって優先度が低く、十分に解決されていない。この「市場規模として利益が出る大きさだが、AI ラボが本腰を入れるほど大きくはない問題」こそが、スタートアップの狙い目だと指摘した。

**ロングテール問題の具体例**

**1. 多言語・文化的ニュアンス**

Arabic や Farsi など非英語言語では AI のパフォーマンスが著しく低下する。CMU 教授のイラン人の友人の体験談：彼女が Farsi のイディオムの意味を正しく説明しても、相手に「ChatGPT の答えと違う、あなたが間違っている」と言われた。ChatGPT は Farsi が苦手にもかかわらず、権威として信じられてしまっている。

**2. 音声チャットボットとレイテンシ問題**

音声チャットボットは speech-to-text → LLM → text-to-speech の 3 ステップを経るため、自然な会話には 800ms 以下が求められる。英語では比較的速いが、Arabic や Russian では合成が遅く自然な会話が困難。また、レイテンシの「好み」自体が文化によって異なる：欧米では会話の間が 18ms 以内を好む傾向があるが、ベトナムなどでは 200ms 程度の間が「相手の発言を理解してから答える敬意ある間」として評価される。Chip 自身の姪（ベトナム人 10 歳）と名付け親（アメリカ人 70 代）の電話でのすれ違いエピソードが紹介された。

**3. ヒューマン AI インタラクション（開発ツール）**

会場の参加者の大半が AI コーディングツールを使用しており、Terminal と IDE の両方を使うと回答した。Chip は Terminal の「意図的に難しく設計されている」性質（rm -rf など危険なコマンドを誤って実行させないための設計）を指摘し、「IDE の使いやすさと Terminal のパワーを兼ね備えたハイブリッド製品が Claude Code Desktop や Codex Desktop」という方向性を評価した。

また、AI コーディングエージェントを「常に動かし続けるために MacBook を開けたまま持ち歩く」問題を指摘し、クラウドベースで動かしてモバイルから制御できる仕組みの重要性を述べた（Telegram ボットで Claude Code を制御した自作プロジェクトを紹介）。

**4. コードレビューとコラボレーションの変質**

GitHub は「コード」を中心的アーティファクトとして設計されているが、AI コーディング時代のメインアーティファクトは「インストラクション（仕様・指示）」になっている。ある会社で体験したケース：シニアエンジニアが今もコードを 1 行ずつレビューしているが、ジュニアエンジニアはそのフィードバックを無視している。理由は「そのフィードバックが actionable ではない」からだ。ジュニアエンジニアが本当に必要としているのは「AI への指示の書き方」についてのフィードバックであり、GitHub は現状そのように設計されていない。「Spec-driven development（仕様書駆動開発）が重要で、良い Spec さえあれば AI に渡すと現行コードより良いコードを生成できる」という考えを示した。

## チャプター5: AI フレンドリーな環境の整備（27:34頃）

AI をより良く機能させるためには、AI のパフォーマンスを向上させるだけでなく、「AI が動作しやすい環境を整えること」も重要なアプローチだと論じた。

**コードベースのリファクタリング市場**

AI コーディングは新規コードベースやモジュール化されたコードベースで特に効果を発揮する。既存の大型コードベース（モノリポなど）は AI フレンドリーではない。そのため、「既存の大型コードベースを AI フレンドリーに改修する」コンサルティング市場が急速に立ち上がっている（大規模モノリポをより小さなリポジトリに分割するなど）。

**API ファーストのデザインへの移行**

過去のソフトウェアはヒトが使う前提で GUI を中心に設計されていた。しかし AI エージェントはビジュアル処理が苦手であるため、企業が GUI デザインから API デザインへとシフトしている。Salesforce など既存ツールの利用がヒト由来からエージェント由来へと変化していくと予測した。

**都市インフラの API 化（物理世界の AI フレンドリー化）**

食品デリバリーロボットの「信号ボタン問題」という興味深い事例を紹介した：小型デリバリーロボットには腕がないため、横断歩道の歩行者ボタンを押せず道路を渡れなかった。これに対して一部の都市は「streetlight API」を整備し、ロボットが API 経由で信号を制御できるようにした。これが「物理世界を AI フレンドリーにする」好例だと述べた。

## チャプター6: 可逆性と AI のリスク管理（31:33頃）

AI に大きな権限を与えることで生じる「取り返しのつかないミス」の問題を論じた。

**Claude Code によるデータベース削除事件（実体験）**

Chip が Claude Code に新しいアプリのデプロイを依頼したところ、Docker の Postgres ポートが別のアプリに使われていることに気づいた Claude Code が「ポートを空けるためにそのコンテナを削除した」結果、別の Postgres データベースが完全に消えてしまった。「バックアップがあったから笑い話で済んだが、実本番環境だったら大変だった」と述べた。

**可逆性の問題**

Git のコミット／リバートのようにデジタル操作には可逆性がある場合が多い。しかし AI エージェントが「フォームの送信」「送金」などを行うと、簡単には元に戻せない。AI に多くのツールと権限を与えることでリスクが指数関数的に増大するため、「いかにミスしにくいシステムを設計するか」が重要な課題だと強調した。

**ロボティクスにおける安全性**

物理世界では可逆性の問題が特に深刻だ。Unitree G1 ロボット（金属製ヒューマノイド）が高齢者介護に使われる場合、転倒や電池切れによる突然の停止は重大な事故につながる可能性がある。Onewheel の電池切れによる転倒事故を類比として挙げ、「バッテリー残量が低下したら複雑な動作を抑える」「自動帰還・充電機能」などの安全機構の重要性を述べた。

## チャプター7: AI エージェントの進化 ― デジタルから物理へ（37:07頃）

AI エージェントのアクションの 3 段階を提示した。

**第 1 段階：トークン生成（初期 ChatGPT/LLM）**
次のトークンを予測する形式。テキスト生成、Q&A、メール作成など。

**第 2 段階：デジタルアクション（現在主流）**
ファイルの読み書き、GitHub API の呼び出し、画像生成 API の呼び出し、検索など。コーディングエージェント（Claude Code、Codex など）がこの段階にある。

**第 3 段階：物理アクション（今後の課題）**
ロボットが実世界で「歩く・拾う・置く・押す・引く」などの物理動作を行う。コーディングエージェントと物理エージェントの根本的な違いは「環境の種類」だけで、「環境から観測→アクション実行」というループ構造は同じだ。

しかし物理環境には「デジタルにおける API ドキュメント」に相当する構造化された記述がない。卵の扱い方（どのくらいの力で割れるか）や歩行制御（どのように足を動かせば倒れないか）を人間は乳児期に長期間かけて身体経験から学ぶが、それに相当するデータがまだ AI には不足している。そこで「ワールドモデリング（世界のモデル化）」が重要な研究領域として注目されていると述べた。

Chip が関与するロボット会社が翌日（Build 2026 の会場）でドッグロボットのデモを行う予定であると告知した。「ヒューマノイドも持ってきたかったが諸事情で断念した」と笑いを取った。

## チャプター8: 個人の防衛可能性 ― キャリア・オーディットの勧め（35:58頃）

セッション終盤では、「プロダクトの defensibility」から「個人のキャリアの defensibility」へと視点を移した。

ChatGPT 登場後に Chip が実際に行った「キャリア・オーディット」の手法を紹介した：
1. 1週間にわたって自分が行ったすべての作業を書き出す
2. 各作業について「これは AI に自動化できるか？」を問う
3. 自動化できるなら「それをすでにやっている会社はあるか？」を問う
4. まだなければそれがビジネス機会になる

「AI 露出度（AI exposure）」という概念を提示した：自分の仕事のどの程度のパーセンテージが AI に代替可能か。この数字が高いほど仕事が自動化されるリスクが高い。

## まとめ

### セッションの結論

Chip Huyen はセッションを以下のメッセージで締めくくった：

- 今存在するあらゆるソフトウェアは複製可能な時代になった
- 「何を作るべきか」「それをどう守るか」が本質的な問いである
- しかし、AI がどれだけ進化しても新たな問題は常に生まれる（「インターネットで人に怒ることも、United の顧客サービスに怒ることも、AI は解決できない」）
- AI が普及することで問題解決の表面積（surface area）は拡大し、むしろ新たなビジネス機会が増える
- 個人としては「AI が自動化できないスキル」を意識的に伸ばすことが重要

このセッションは個人講演であるため、特定の Microsoft 製品の GA/Public Preview/Private Preview 発表は含まれていない。ただし、以下の製品・サービスが言及された（登壇者の実体験や事例として）：

- **Claude Code**（Anthropic）: 実際に使用中のコーディングエージェント。デモとして「Postgres データベース削除事件」を語った

- **GitHub**（Microsoft）: コードレビューとコラボレーションが AI 時代に変質している文脈で言及
- **METR ベンチマーク**: AI が 50% の確率で完了できるタスクの長さを計測。現在 16 時間規模のタスクに達している
- **Unitree G1 ロボット**: 物理 AI エージェントのリスク事例として言及
