**登壇者**: Burke Holland（Microsoft、VS Code チーム、司会）、Joanna Oikawa（Microsoft、VS Code デザインリード）
**セッションURL**: https://build.microsoft.com/en-US/sessions/LIVE156

## 全体像

本セッションは、Burke Holland が VS Code のデザインリード Joanna Oikawa にインタビューする形式で進んだ約13分の対談である。テーマは「エージェント時代における VS Code の UX 設計」で、複数エージェントを並列実行するという新しいユーザー行動に VS Code がどのように UI を進化させてきたか、その舞台裏が語られた。

VS Code のデザインチームは設計者4名という小規模な体制ながら、エンジニアも UX オーナーシップを持つ文化によって高速に動いている。Joanna は Figma 上のプロトタイプを画面共有しながら、出荷に至らなかった設計案（Almost Shipped Designs）から最終的に出荷した「エージェントウィンドウ（Agents Window）」の形に至るまでの設計の変遷を説明した。全体を通じて「追加しすぎない」「スクリーン上の全要素を問い直す」という節制の哲学が強調されており、AI 時代のデザイン意思決定における「デプスとテイスト」の重要性が議論の核心となった。

---

## チャプター 1: Agents パネルから Agents Window へ——設計の変遷（00:00頃）

Joanna は Figma を画面共有しながら、2025年12月時点の初期プロトタイプを紹介した。当初のチームの問いは「エージェントを確認・切り替えするのをどう簡単にするか」であり、最初の案はコマンドセンターの検索バーに付属するドロップダウンメニューとしてのエージェント一覧だった。現在の製品にも類似したメニューが存在するが、フィードバックを重ねるうちに「フルスクリーン体験」の必要性が浮上した。

その後、同じエディターウィンドウ内でウェルカムページ相当の場所を起点とした全画面ビューのプロトタイプへと発展した。最終的に出荷されたものはそれに近い形だが、最も変わったのは「何の情報をここに表示すべきか」という情報設計の部分だった。ユーザーリサーチと大量のフィードバックを通じ、ユーザーが望んでいたのは「異なるプロジェクトをまたいでセッションを一覧できること」であると判明し、この洞察が最終仕様の決定打になった。

## チャプター 2: 設計意思決定のプロセス——インサイダービルドと継続的改善（02:50頃）

Burke から「どうやって正しいデザインを選ぶのか」と問われ、Joanna は設計の難しさを「既存のパターンと既存ユーザーの習慣が存在する製品に、まったく新しい使い方を追加しようとしている」という言葉で表現した。エージェントという新しいモダリティはチーム自身もユーザーも同時に学んでいる最中であり、「走りながら船を作っている（building the boat while it's running）」状態だという。

意思決定の手順はおおよそ以下のとおりである。まず VS Code Insiders ビルドにデプロイし、実験的展開を行う。次に社内外のユーザーリサーチを実施してデータを収集する。その後もフィードバックに基づいて問題空間を繰り返し触り続ける。チームとして「最終版」を宣言することはなく、納得いくまで改善を続ける文化がある。Burke が「UI Power Hour という取り組みがあると AI が言っていたが」と聞くと Joanna が「それは知らない」と答え、会場の笑いを誘う一幕もあった（AI によるハルシネーションとして Burke が認めた）。

## チャプター 3: Figma MCP とデザイナーによるコード直接出荷（04:25頃）

Joanna は Figma MCP（Model Context Protocol）の活用について言及した。これにより「Figma のデザインをコードに素早く変換する」だけでなく、逆方向の「コードから Figma コンポーネントを更新する」双方向のワークフローが可能になった。設計者はどちらのツールからでも作業でき、最も効率的な方法を選べる。

VS Code デザインチームでは、全デザイナーが実際にコードも書いてプルリクエスト（PR）を提出している。David Dossett のような一部の元デザイナーはコードベースへの深い関与を昔から行っていたが、全員が PR を出すのは比較的新しい変化である。チームは現在も「どのタイミングで PR を出すべきか、プロトタイプを作るだけでよいか、Figma で留めるべきか」のバランスを模索中だと Joanna は述べた。

また同じ12月当時の Figma ファイルとして、テーマのカラーリフレッシュ（新しい視覚スタイルの実験）のプロトタイプも共有された。パネルの影、背景より明るいパネルカラーなどのオプションが検討されたが最終的には変更された。VS Code アイコンが点滅するアニメーションも一時案として存在したが「少しうるさすぎる」というフィードバックで取り下げられ、現在の「アップデートボタン」へと進化した。

## チャプター 4: 「全員がデベロッパーであり、全員がデザイナー」——デプスとブレッドスの新しい均衡（06:15頃）

Burke は「PM もデザイナーも PR を出すようになった。今や全員がデベロッパーだと言えるのか」と問いかけた。Joanna はそれを肯定しつつも、重要なのは「デプス（専門深度）とブレッドス（幅広さ）の考え方」だと語った。自分の深い専門領域はユーザーエクスペリエンスとビジュアルデザインに変わらずあるが、AI によって今まで難しかった領域にも手が届くようになった。

具体例として、Kusto クエリ（Microsoft 社内のテレメトリデータ照会言語）の話が挙がった。以前はテレメトリデータを読むために専任の担当者（Burke が「Devon」という名前の人物を例示）に依頼する必要があったが、AI の助けで Joanna 自身が Kusto クエリを書いてデータドリブンな意思決定を行えるようになった。「アナリスト帽、PM 帽をかぶれるようになった」という表現で、AI による個人の能力範囲の拡大を評価した。

Burke は将来的にデプスの違う専門職が消えてしまうのではないかと懸念を示したが、Joanna は「相互に補完し合う深度が重要で、エンジニアは私のアイデアに対して『それはアプリを遅くする』と指摘できる、そのような専門性の組み合わせが製品のバランスを保つ」と反論した。

## チャプター 5: AI による「デザイン幻覚」と節制の哲学——テイストの育て方（08:44頃）

Burke は「AI サイコシス（AI psychosis）」という表現で、AI がデザインを生成すると自分が優れたデザイナーになったと錯覚する現象を描写した。「Claude（Opus）などで作ったと自慢して見せてくれたものが、紫とグラデーションだらけで見るに堪えない」という実体験を語り、「誰かが『それはやめよう』と言える人間が部屋にいる必要がある」と指摘した。

これを受け Joanna は「それがまさにデプスとテイスト（taste）の価値だ」と述べた。テイストは経験の蓄積から生まれるが、AI が作業を全部やってしまうと「失敗から学ぶ」機会が失われるのではないかという Burke の問いに対し、Joanna はバリデーションループ（validation loop）の重要性を強調した。出荷したものが意図した問題を本当に解決しているかフィードバックを取り続け、うまくいかなければ取り除く。「追加し続けることは簡単だからこそ、取り除く自律心が必要だ」というメッセージである。

Burke も「絵を描いていると、これ以上描くと悪化するというポイントがある。AI でも同じで、全機能を追加できても、すべきかどうか考えて止まることが大切だ」と例えで同意した。この「どこで止めるか」の感覚こそが Agents Window の設計において中心的なテーマになったと Joanna は明言した。

## チャプター 6: Agents Window の設計原則——情報の「引き算」による集中体験（11:28頃）

Joanna は Agents Window の設計の核心を「複数エージェントを並列実行するカオスを補完するための、集中できる場所を作ること」と定義した。そのためには「VS Code で歴史的にオプションだったものを引き算する」判断が必要だったという。

Figma の最新プロトタイプを画面共有しながら、チームがどのように「別ウィンドウ・別スペース」として複数プロジェクトにまたがる俯瞰ビューを設計したかを説明した。画面上のすべての要素に対して「これは今この瞬間の意思決定を助けるか、それとも情報・選択肢・気散じを増やすだけか」を問い続けたという。

具体的に悩んだのは次の点である。出力表示はどのような形にすべきか。セッションリストには何の情報が必要か。朝の作業開始時に複数エージェントをまとめて確認するために何が必要か。そして重要なのは「あまりにも多くのことが同時に起きていて制御不能に感じさせない」ユーザー体験とのバランスである。情報を足すのではなく削ることで「集中」を実現するというこの設計哲学が、Agents Window の本質であると語った。

## まとめ

### セッション全体の結論

本セッションは、Joanna Oikawa が VS Code の設計チームとして「エージェントウィンドウ」をどのように設計・反復してきたかを Figma プロトタイプの実演を交えながら解説したインタビュー形式の対談である。技術的な新機能の発表よりも「AI 時代の UX 設計思想」に重点が置かれており、追加より削除・テレメトリと研究による意思決定・全員がデザイナーかつデベロッパーである文化・バリデーションループによるテイストの育成、という四つの柱が一貫して語られた。

### 発表された新機能・取り組み（ステータス）

| 機能・取り組み | 内容 | ステータス |
|---|---|---|
| **Agents Window（エージェントウィンドウ）** | 複数エージェントを並列管理するための VS Code 内フルスクリーン専用ビュー。複数プロジェクトをまたいだセッション一覧が可能 | 出荷済み（現行バージョンに搭載） |
| **Figma MCP 連携** | Figma のデザインとコードの双方向同期。デザイナーが PR を提出しコードとデザインを同時更新できるワークフロー | 採用済み（チーム内で実運用中） |
| **テーマ・カラーリフレッシュ** | パネルの影・背景色との明度差など視覚スタイルの実験的更新。フラッシュアニメーション案は却下されアップデートボタンとして実装 | 一部出荷済み、継続改善中 |
| **VS Code Insiders を使ったテストロールアウト** | 新 UI をまず Insiders ビルドで段階展開し、フィードバックと研究に基づいて安定版へ移行するプロセス | 既存運用プロセス（継続中） |

### 技術者向けの次アクション

1. **Agents Window を実際に使ってみる** — 現行の VS Code で Agents Window を開き、複数プロジェクトにまたがったエージェントセッションの一覧機能を確認する。設計の「引き算」がどう体験に反映されているか自分で評価する。
2. **Figma MCP を自分のデザイン・開発ワークフローに取り込む** — Figma と VS Code（あるいはコードベース）の双方向同期を試し、デザインと実装のループを短縮できるか検証する。
3. **バリデーションループを意識した開発習慣を作る** — AI を使って機能を素早く実装した後、必ず「これは元々解こうとしていた問題を解決しているか」を問い直す検証ステップを設ける。
4. **VS Code Insiders ビルドで最新 UX 実験を追う** — デザインチームは新しいアイデアをまず Insiders に展開する。フィードバックを送る最速の手段として Insiders チャネルを使う。
5. **デプスとブレッドスのバランスを見直す** — AI を活用してテレメトリ分析・プロトタイピング・コード実装など越境的な作業を行いながらも、自分のコア専門性をどこに置くかを意識的に定義する。
