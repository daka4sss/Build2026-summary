## 全体像

本セッションは Microsoft Foundry を基盤として、進化し続けるAIモデルとコストの変化の中で「賢いAIシステム」を構築・維持するための方法論を実演形式で解説した約45分のセッションである。対象は企業でエージェンティック（自律型）AIシステムを構築・運用している開発者。

「モデルを選んで繋いでシップする」という一年前の単純なアプローチから、長期稼働するエージェンティックシステムの継続的改善という複雑な現実へのシフトを問題定義として示し、その解として「評価（eval）を最初に定義し、ヒルクライム（継続的改善）でシステム全体を最適化する」という思想を一貫して訴えた。

セッションは「Selection（選定）→ Evaluation（評価）→ Optimization（最適化）→ Scaling/Operations（運用）」という4フェーズ構成で進む。デモシナリオとして「社内旅行申請アプリ（Trip Planning Agent）」を使い、GPT-4.1 ベースラインからマルチモデルルーターへの切り替え、カスタム評価、ファインチューニングまでの改善ループを実演した。

## 1. セッション冒頭：問題提起と思想的フレームワーク（0:00頃）

Yina が冒頭に開発者が直面する三つの課題を明示した。

- **モデル選定の難しさ**: 毎日新モデルが登場し、ベンチマークは自社シナリオへの適合を保証しない
- **コストの予測困難さ**: 開発中は問題なくても本番運用で請求額を見て驚く
- **景色が変わり続ける問題**: ようやくシステムを完成させたら、次のモデルや次のツールへの対応が必要になる

これらへの解として提示されたのが「**評価（eval）ファースト**」の考え方である。従来の「先にビルドしてQAは最後」というアプローチを完全に反転させ、**成功基準とevalを最初に定義し、それを測定棒として継続的に改善する**設計思想を採用すべきと主張した。これをセッション全体の核心メッセージと位置づけた。

Microsoft Foundry がプラットフォームとして提供する価値として、以下を列挙した。

- **Foundry IQ**: エージェントへのコンテキスト・知識グラウンディング
- **Work IQ**: Microsoft 365 の生産性データ連携
- **Fabric IQ**: 構造化データ連携
- **Web IQ**: Web上のナレッジ活用
- Foundry Hosted Agents による実行基盤
- A365（Agent 365）によるガバナンス

Naomi がモデル選定の考え方を解説した。モデルは「すべてのユースケースに1つを選ぶ」のではなく、「タスクごとにモデルを決めるシステム設計上の意思決定」として捉えるべきであるとした。

### Foundry モデルカタログの現状

- **11,000以上のモデル**を提供（OSS・クローズドの双方）
- 統一 API とエンタープライズキュレーションを提供
- フラッグシップモデル: OpenAI（GPT-5.4/5.5系 など）、Anthropic（Claude）
- Hugging Face との深いパートナーシップによる OSS モデル大量収録

### 新発表（アナウンス）

**Claude on Azure（GB300ハードウェアで稼働）** — 本発表。Claude Opus 4.8 が先週 Foundry カタログに追加済みで、さらに今回「Claude が Azure のインフラ上で実際に稼働する」形態を発表。Azure GB300（最高グレードのハードウェア）で稼働し、Anthropic の開発ツール群が Azure から直接利用可能になる。会場の反応を見て Naomi が「少なくとも一人は Claude に興奮している」とコメントし笑いを誘った。

**Microsoft AI ファーストパーティモデル（Build 2026 キーノート同日 GA）** — Mustafa のキーノート中にチームがプッシュし、当日ライブで公開。思考・画像・コード・音声のフルマルチモーダルスタックを構成。特に **Image 2.5** を強調。

**NVIDIA との拡張パートナーシップ** — 以下を Foundry に追加：
- **NVIDIA Nemotron** ビジョン・推論モデル
- **NVIDIA Cosmos**（フィジカル AI 向け）
- **NVIDIA Earth-2** 天候予測モデル
- 物理 AI 向けプレ録画デモセッションも別途用意

**目的特化型モデルの台頭** — ジオスペーシャル・ロボティクス・バイオメディカル・材料科学・コード検索・メディアなど各ドメイン向け専用モデルが拡充。具体例として **Aurora 1.5**（衛星画像・大気データを活用した最先端気象モデル）を紹介。

**Foundry Labs** — Microsoft Research から最先端の実験的モデルを提供する新チャンネル。プロダクション用の安定モデルと研究フロンティアの両端をカバーする戦略を表明。

## 3. デモシナリオの設定とベースライン計測（13:14頃）

デモでは「従業員旅行申請エージェント（Trip Planning App）」を軸に進行した。このアプリは企業内での典型的なシナリオ——意図の把握、ルールに基づく判断、ユーザーへの回答——を再現している。

### ベースライン設定

- 初期データ: 20行のシードデータ
- モデル: GPT-4.1（1モデルをすべてのタスクに使用）
- 評価指標: task adherence（タスク遵守）、task completion（タスク完了）などの組み込み評価器

**結果（ベースライン）**:
- 品質スコア: **0.59**（目標: **0.8**）
- コスト/タスク: 高コスト
- レイテンシ: 許容範囲

Naomi が「1モデルで全タスクに対応するのは、フェラーリで買い物に行くようなもの」と表現。ベースラインは出発点に過ぎず、この段階で「何を改善すべきか」が明確になることが重要と強調した。

## 4. モデルルーターによる最適化：タスク分解とルーティング（17:45頃）

Yina が「マイクロサービスアーキテクチャ思考」をAIシステム設計に適用する考え方を提示。ソリューション全体を単一モデルで処理するのではなく、タスクを分解し、それぞれに最適なモデルを割り当てる。

### Foundry モデルルーター

- 対応モデル数: **28種類**
- 対応モデル例: GPT-5.4、GPT-5.5 ファミリー、Claude Opus シリーズ
- 自動フェールオーバー機能搭載
- エージェンティックワークフロー対応
- **本日新発表**: ガバナンスポリシーにより「モデルルーターが選択できるモデルの範囲」を管理者が制御可能になった（パブリック発表）
- 今後: ルーター自体のカスタマイズ・ファインチューニング、ファインチューニング済みモデルの組み込みを予定

### 自前ルーターの実装例

GPT-4.1 Nano や Mistral Small などの小型モデルで意図分類を行い、タスクに応じてより大きなモデルへルーティングする設計パターンもデモで紹介。

**マルチモデルルーター後のスコア**:
- 品質スコアが上昇
- コスト/タスクが大幅に改善（目標に近接）
- レイテンシは引き続き改善対象

## 5. Evaluate フェーズ：カスタム評価とルーブリックベース評価（22:41頃）

Yina がここでセッション最重要メッセージを再強調：「評価（eval）は単なるQAではなく、**プロダクト仕様**であり、**知的財産（IP）**だ。」

### 評価の3層構造

Foundry の評価カタログには以下が含まれる。

1. **組み込み評価器（Built-in）**: 品質（intent adherence、relevance、task completion）、リスク・安全性（ハルシネーション検出、有害コンテンツ）
2. **エージェンティック評価器**: マルチターンにわたるエージェントの行動を評価
3. **カスタム評価器**: プロンプト・コード・ルーブリックの3種類

### 新発表：ルーブリックベース評価器（Rubric-based Evaluators）

- 本日 Microsoft Build にて発表
- 既存エージェントの定義（プロンプト・設定・軌跡サンプル）を読み込み、**LLM が自動で評価次元（ルーブリック）を生成**
- 各次元のウェイトを手動調整可能（例: ポリシー遵守の重みを 5→8 に変更）
- 実行後にクラスター分析でハルシネーション箇所・不十分な回答箇所を可視化
- UIからもコードからも利用可能

**デモ結果**: 旅行エージェントのルーブリックとして7次元が自動生成された（policy compliance、correctness、tool call validity、escalation accuracy、safety、privacy 等）。LLM ジャッジによる汎用評価では policy compliance を適切に計測できなかったが、ドメイン知識（旅費規定ファイル）を使ったカスタム評価で「まだポリシー遵守が不十分」という具体的な問題が特定された。

## 6. Optimization フェーズ：コスト・レイテンシ・品質の複合最適化（28:53頃）

「AI コスト削減は安いモデルに替えることではなく、**アーキテクチャの意思決定**から生まれる」という命題のもと、複数のレバーを解説した。

### コスト最適化レバー（スタック可能・複利効果あり）

| レバー | 説明 |
|---|---|
| ルーティング | ワークロード別に適切なモデルへルーティング |
| バッチ推論 | 非同期ジョブで大幅コスト削減 |
| 構造化出力 | 無駄なトークンを削減 |
| キャッシング | 繰り返し処理を回避 |
| 蒸留（Distillation） | 大型モデルの知識を小型モデルに転移 |

### 新発表：Azure Context Cache（Explicit Prompt Caching）— Private Preview

- **本日 Private Preview 開始**として発表（会場から拍手）
- 従来の暗黙的キャッシングから「**明示的プロンプトキャッシング**」へ進化
- キャッシュの所有権が**推論プロバイダーではなくユーザー側**に帰属
- 自社のデプロイメントとコスト削減状況を直接確認可能
- プライバシー管理の向上と長時間タスクの可用性向上を実現

### レイテンシ最適化

- タスクごとに高速モデルへルーティング
- PTU（Provisioned Throughput Unit）で予約キャパシティ確保
- ストリーミングによる体感速度向上
- API ゲートウェイによるトラフィック分散
- 優先処理（Priority Processing）による低遅延経路の確保
- 「**本番レイテンシは設計するもの、祈るものではない**」と強調

### 品質最適化の段階的アプローチ

軽量→重量の順にレバーを使うことを推奨：

1. プロンプト設計（まず最初にやること）
2. コンテキストの改善・RAG
3. 分解とルーティング
4. ファインチューニング・蒸留
5. カスタムモデルトレーニング（最重量）

## 7. Fine-tuning と Post-training：蒸留による品質改善デモ（34:57頃）

policy compliance の低スコアを解決するため、**蒸留（Distillation）+ ファインチューニング**を適用するデモを実施した。

### 実施内容

- 大型「ティーチャーモデル」で旅費規定の知識を学習させ、その知識を **GPT-4.1 Nano** の小型モデルへ転移
- Python コード 100行未満でジョブをサブミット
- 「デベロッパーティア」を使って低コストでファインチューニングモデルをテスト

**結果**: ファインチューニング後の GPT-4.1 Nano が目標品質スコア（0.8）を達成。コスト最適化を維持しながら policy compliance を解決。

### Foundry の Post-training メニュー（3層構造）

| 手法 | 概要 |
|---|---|
| Managed Fine-tuning | 最も簡単。データを渡すだけで Foundry がデータ準備・学習・監視・デプロイをすべて管理。SFT / DPO / RL を選択可能 |
| Serverless RL API（本日 Build にて発表） | 報酬関数とハイパーパラメータをユーザーが制御し、インフラは Foundry が管理。LoRA ウェイトを生成しオーバーレイ適用。クラスター管理不要 |
| Full-control RL | コード・分散戦略・アルゴリズム・GPU 種別まで完全制御。Foundry がコンピュートとオーケストレーションを管理。SLIME / VERL 等フレームワーク対応 |

カスタムモデルの展開先として、オープンソースモデルは **Fireworks on Foundry**（Managed Compute）または自社コンピュートクラスターを利用可能。

### 新発表：Fireworks AI との GA パートナーシップ

- **本日 GA（一般提供開始）**として発表
- ゼロデイアクセスで最新フロンティアモデルへのアクセス
- ベストインクラスの推論パフォーマンス
- Azure エンタープライズスタック（認証・API・SDK すべて統一）とのネイティブ統合

Hugging Face との Managed Compute パートナーシップも引き続き強化。Hugging Face・NVIDIA・Microsoft Research から数千モデルを取り込み、vLLM・SGLang・NVIDIA NIM ランタイムで効率実行。

## 8. Scaling/Operations：本番観測性とクロージング（40:48頃）

システムが本番稼働後、「規律ある運用」としてオブザーバビリティ（可観測性）の重要性を解説した。

### Foundry の観測性スタック

- **Tracing**: プロンプト・ツール呼び出しのエンドツーエンド可視化

- **Azure Monitor 統合**: コスト・レイテンシのリアルタイムシグナル
- **Copilot 支援**: Foundry ポータル内で「この指標を改善するには？」と Copilot に直接質問できる機能をデモ

CI/CD パイプラインへの統合、バージョニング、ロールバック機能も GitHub インテグレーションを通じてサポートされていることを強調した。

## まとめ

### セッションの核心メッセージ

1. **evalファースト**: 成功基準と評価を先に定義し、それを「プロダクト仕様かつIP」として扱う
2. **タスク分解 × マルチモデル**: 1つの大型モデルですべてを処理するのでなく、マイクロサービス思考でタスクごとに適切なモデルを選択
3. **複利的最適化**: コスト・レイテンシ・品質のレバーは積み重ねることで効果が倍増する
4. **継続的改善**: モデルライフサイクルの変化に耐えうる「測定可能な改善ループ」を持つシステムを構築せよ
