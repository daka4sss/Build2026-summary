## 全体像

本セッションは、オープンソースの推論モデルを Microsoft Foundry 上で「post-training（ポストトレーニング）」し、エージェントとして本番デプロイするまでの一連のワークフローを、デモを交えて深掘りする技術セッションである。

メインメッセージは「モデルを本番に出すのはスタートに過ぎない」という点だ。エージェントはツールコールを何度も繰り返すため、フロンティアモデルをそのまま使い続けると推論コストが急騰する。そこで、生産トレースを活用した Supervised Fine-Tuning（SFT）と Reinforcement Fine-Tuning（RFT）を組み合わせ、より小型・低コストのオープンソースモデルをフロンティアモデル品質まで引き上げる手法を紹介する。

デプロイ側では、トレーニング済みモデルを Foundry Managed Compute（新機能）でサーバーレスかつスケーラブルに運用できる仕組みが発表された。エバリュエーション→ファインチューニング→デプロイ→観測という継続的改善ループ全体が Foundry の単一プラットフォームで完結することが、本セッションの核心である。

## Chapter 1: セッション導入 ── エージェント時代のコスト問題（0:00頃）

Chris が登壇し、エージェント活用の急拡大とそれに伴うコスト課題を解説した。

- エージェントは通常のチャットボットに比べ **大幅にトークンを消費する**。その理由は、エージェントが企業システム・データベースと連携しながら複数回のツールコールとループ処理を実行するため。
- フロンティアモデルはデフォルトで高品質だが、ツール選択や Course Correcting の試行錯誤が課金コストに直結する。
- エージェントをスケールさせるほど請求額も比例して増大する、という「コストのスケーリング問題」が浮上している。
- 解決策として **post-training（ファインチューニング）** が有効。モデルにビジネスドメイン・ツール使用パターン・ポリシーを学習させることで、無駄なツールコールを削減し「より速く、より良く、より安く」動くエージェントを実現できる。

## Chapter 2: モデル選定とエバリュエーションの考え方（0:04頃）

Foundry 上でのモデル選定フローを解説。

- Foundry にはオープンソース・プロプライエタリ問わず膨大なモデルカタログが存在し、随時追加されている。
- 「正しいモデル選択」の方法論は **科学的手法（guess and check）** すなわちエバリュエーションである。
- デモでは小売業の返品対応エージェントシナリオを使用。GPT-5 シリーズと **Qwen 32B / 14B**（オープンソース）を比較した。
  - GPT-5 はそのままでも高性能だが、より小型のモデルをファインチューニングで同等品質まで引き上げることでコストを **10分の1以下** にできる可能性がある。
- **Eval（エバリュエーター）の定義が最重要ステップ**。Eval は単なるモニタリングツールではなく「プロダクト仕様書」であり、デプロイ前に成功基準を明確化するものである。
  - ポリシー遵守・正しいツール呼び出し順序・応答品質など複数軸を同時最適化する「多次元最適化」の枠組みとして捉える。
  - Foundry には組み込みエバリュエーターに加えカスタムエバリュエーターを作成できる機能がある。
- デモでは retail_quality（小売品質）という統合カスタムメトリクスを定義し、複数エージェント世代を比較。初期バージョンは 76% 品質で目標の 90% には届かず、これをポストトレーニングで引き上げることがデモのゴールとして提示された。

## Chapter 3: Post-Training の理論 ── SFT と RFT の仕組み（0:12頃）

Vijay が登壇し、post-training の技術的背景を体系的に説明した。

### モデルトレーニングの 3 フェーズ

| フェーズ | 内容 | 規模 |
|---|---|---|
| **Pre-training** | 世界知識を大規模データで学習 | 最大のデータ量・計算量 |
| **Mid-training** | 言語・コーディングなど専門知識の注入 | 中規模 |
| **Post-training** | 特定タスク・エージェントワークフロー向けに最適化 | 小規模・低コスト |

Post-training は OpenAI・Anthropic など大手ラボが使う言葉であり、**fine-tuning・RLHF などを包括するアンブレラタームである**。

### Post-Training のレシピ

今回のデモで採用したレシピ：**「蒸留（distillation）→ SFT → RFT」の 3 ステップ**。

1. **データ蒸留**: 本番エージェントの production traces を収集し、フィルタリングして SFT/RFT 用データセットを作成。データソースは production traces・RLHF（人間のフィードバック）・合成データのいずれでも可。
2. **SFT（Supervised Fine-Tuning）**: 専門家の模範応答を学習データとして、モデルに「tone・format・ツール呼び出しパターン」を模倣させる。損失関数で予測値と正解値の近さを測定し、モデルの重みを更新する。
3. **RFT（Reinforcement Fine-Tuning）**: SFT より複雑だが効果が大きい。検証可能なタスク（コーディング・数学・ポリシー遵守など）に有効。プロンプトに対して複数のロールアウト（応答軌跡）を生成し、各ステップにリワード（報酬）を与えることで、モデルが「模倣」だけでなく「正解に到達するための経路を自律的に探索」できるようになる。

## Chapter 4: デモ ── Code-First アプローチによる SFT/RFT ジョブ実行（0:20頃）

Vijay によるライブデモ。ハプニング：デモ開始直後に PC がロックされる場面があったが（字幕 "It got locked up"）、すぐ復旧した。

### Workbench（コンピュートインスタンス）の利用

- Foundry の **Workbench** にアクセスすると、GPU クラスター・依存ライブラリ・ネットワーク設定が事前に構成済みの VS Code 環境が立ち上がる。
- ユーザーは pip install などの環境構築なしにすぐコードを実行できる。

### SFT ジョブの実行

- データセット（production traces から蒸留済み）を指定する。
- GPU クラスター設定（ノード数・トポロジー）を指定してジョブをキック。
- SFT ジョブはモデルのチェックポイントを逐次生成し、各チェックポイントを個別にデプロイ可能。
- ジョブ完了後、そのモデルを RFT の初期モデルとして使用する（ただしデモ時間の都合で、事前に完了済みのジョブ結果を利用）。

### RFT ジョブの実行と Ray による分散処理

- RFT ジョブは **Ray** クラスターで動作。Ray は分散 Python 処理エンジンであり、複数 GPU ノードにわたってロールアウト・勾配計算を並列実行する。
- Foundry の UI から Ray ダッシュボードを直接参照でき、**各ノード・各 Actor の CPU/GPU リソース使用率** をリアルタイムで確認可能。
- 「fire and forget」な API とは異なり、**ジョブ内部の詳細な可視性**（どの Actor が何を実行しているか）が提供される。

### ロールアウトのデバッグ

- RFT 実行中のロールアウトを UI から確認可能。各サンプルについて「どのツールを、どの順序で呼んだか」と「リワードスコア」を並べて表示。
- 例: Prompt 8（返品理由照会）では必要なツール呼び出しを省略していたためスコアが低く、Rollout 16 では正しい順序でツールを呼んでいるためスコアが高い、といった原因分析が UI から直接行える。

## Chapter 5: 結果比較 ── Post-Training による品質・コストの改善（0:30頃）

デモの結果として、各モデルのエバリュエーションスコアが比較提示された。

| モデル | 条件 | pass rate |
|---|---|---|
| GPT-5.2（フロンティア） | ベースモデル | 高（基準点） |
| Qwen 14B | ベースモデル（ノートレーニング） | 低（ほぼ 0） |
| Qwen 14B | SFT 後 | 上昇 |
| Qwen 14B | SFT + RFT 後 | さらに上昇（目標品質に接近） |

- Qwen 14B はベースでは GPT-5.2 より大幅に劣るが、**distillation + SFT + RFT の組み合わせにより pass rate が段階的に向上**し、はるかに低コストでフロンティアモデルに匹敵する品質を達成できることが示された。
- ポストトレーニングはループ処理で繰り返し実施可能であり、各イテレーションでエバリュエーションと組み合わせて品質を継続的に Hill Climbing（最適化）できる。
- RFT 実行中のメトリクスとして「リワードの上昇」「エントロピーの低下」「グループ相対比較スコアの上昇」が確認された（GRPO アルゴリズムを使用していると推測）。

## Chapter 6: 低レベル API「Loom」── ノート PC から GPU ジョブを投入（0:32頃）

Vijay がコードファースト体験に加えて、新しい **低レベル GPU API**（コードネーム: **Loom**）を紹介した。

### Loom の特徴

- GPU クラスター・イメージ・環境・ネットワーキングの管理を**サービス側が全て担う**。
- ユーザーは以下の **4 つの GPU プリミティブ** だけ理解すれば良い：
  1. Forward pass
  2. Backward pass
  3. Gradient の最適化（loss function の評価）
  4. ロールアウトの sampling
- RL ロジックを**ノート PC の CPU 上で記述**し、ジョブを投入するとサーバー側の GPU クラスターで実行される。

### ユースケース

組織全員が GPU を持つわけではないが「全員がノート PC を持つ」という現実に対応する設計。データサイエンティストでなく、RL の挙動を細かく制御したいパワーユーザー向け。

例：数学を教える際に「まず四則演算→次に代数→最後に線形代数」と**難易度を段階的に上げる curriculum learning** を、クライアントサイドのカスタムロジックとして実装できる。

### Foundry の Fine-tuning UI との統合

Loom API で投げたジョブも、Foundry の「Fine-tune」メニューに SFT・RFT 問わず同一ビューで表示され、ログ・チェックポイント・メトリクスダッシュボードが統一的に利用できる。

## Chapter 7: Foundry Managed Compute ── デプロイメント新機能（0:36頃）

Chris がトレーニングからデプロイへの接続を解説し、Manoj がデモを担当した。

### Foundry Managed Compute（本 Build にて発表）

- **概要**: オープンソースモデル・カスタムモデルのいずれも、サーバーレス・スケーラブルに Foundry 上でホスティングできる新オファリング。
- **対応モデルの範囲**:
  - Foundry でトレーニングしたモデル（SFT/RFT 済みの fine-tuned モデル）
  - 他のプラットフォーム（ノート PC 含む）でトレーニングして**ウェイトを持ち込んだモデル（BYOW: Bring Your Own Weights）**
  - カスタムコンテナを持ち込んだモデル（speculative decoding や draft models など高度に最適化されたランタイムも対応）
- **デプロイフロー**:
  - モデルカタログから対象モデルを選択（デモでは Qwen 32B を使用）
  - デプロイメントオプションで「Managed Compute（Global）」を指定
  - GPU 数と Context Length のトレードオフをテンプレートから選択（例: 2 GPU で 128K context、または 1 GPU で 40K context）
  - Fine-tuned モデルのデプロイはベースモデルとまったく同一のフロー（差異なし）
  - 他環境でトレーニングしたモデルは import model コマンドでプロジェクトに登録し、ベースモデルのアーキテクチャを指定することで自動的に適切なコンテナ・設定が選択される
  - full weight モデルまたは adapter（LoRA 等）の別を指定するオプションあり

### Responses API サポート

- デプロイした fine-tuned モデルは **Chat Completions API** と **Responses API** の両方をサポート。
- Responses API により**会話履歴をサービス側が管理**（ステートフル）。デモでは「前のターンで言った好きな色を覚えていますか？」というクエリに、チャット履歴を渡さなくても正しく答えられることを確認した。

### 可観測性・コスト管理

- デプロイ後の**トークン消費量・コスト・レイテンシー**などを Foundry の統合ダッシュボードで監視可能。
- カスタムチャートをダッシュボードに追加できる。
- Qwen モデルを例にフィルタリングしてコスト追跡するデモを実施。

## Chapter 8: まとめと利用開始ガイド（0:44頃）

Chris によるセッション総括。

- ポストトレーニングの **継続的改善ループ** は以下のサイクルで回せる：
  1. 本番エージェントをデプロイして production traces を収集
  2. traces を Foundry のデータセットに変換
  3. SFT / RFT で小型モデルを改善
  4. エバリュエーターでスコアを検証
  5. 合格したらデプロイ → 1 に戻る
- RL フレームワークは **slime（verl の誤認識の可能性あり：推測）**・**TRL**・Ray など既存のオープンソースフレームワークをそのまま利用可能。
- サンプルリポジトリは本 Build セッション後に公開済み。

### 発表新機能

| 機能名 | ステータス | 概要 |
|---|---|---|
| **Foundry Managed Compute** | **本 Build で発表（利用可能）** | オープンソース・カスタムモデルをサーバーレスで GPU ホスティング。BYOW・カスタムコンテナ対応。auto-scale、context length 選択可。 |

### 技術的結論

本セッションで示されたデータによれば、Qwen 14B はベースモデル単体では品質が低いが、production traces からの蒸留 → SFT → RFT のパイプラインを経ることで、GPT-5.2 に近い品質に達しながらコストを **10 分の 1 以下** に抑えられる可能性がある。これは、エージェントを大規模運用する企業において、post-training が「コスト管理と品質維持を両立させる」実践的な戦略であることを示している。
