## 全体像

本セッションは、Microsoft Azure AI Foundry の知識接続プラットフォーム「Foundry IQ」の設計思想・新機能・デモを中心に構成されている。Foundry IQ は「エージェントとAIモデルを、企業内のあらゆる知識ソースに繋げる」ためのプラットフォームであり、登壇者は冒頭で三つの設計原則を提示した。(1) **簡単に始められること**、(2) **成長に応じた柔軟性（versatility）**、(3) **ランキング・関連性・コンテンツ理解における最高品質**、の三点である。

セッション全体を通して、ファイルアップロードから MCP サーバー化、サーバーレスプロビジョニング、Fabric・Microsoft 365・Web との統合、セキュリティ（Entra / Purview 連携）、Agentic Retrieval の改善、そして検索レイテンシのデモと多岐にわたる内容が扱われた。デモはすべてライブで行われ、一部で軽微なトラブル（GitHub Copilot の MCP 設定画面が一度消えてしまう、設定のやり直し）が発生したが、落ち着いてリカバリーした。

## セッション開幕・Foundry IQ の設計原則（0:00頃）

Pablo は Foundry IQ チームに所属することを自己紹介し、セッションのゴールを「エージェントとAIモデルを、それらが必要とするデータ・知識に接続するために何が必要かを話し合うこと」と説明した。三つの設計原則として以下を挙げた。

- **Easy to get started（簡単な開始）**: まずは手軽に試せること
- **Versatility（汎用性）**: アプリが複雑化しても同じプラットフォームで対応できること
- **Top quality（最高品質）**: ランキング・関連性・コンテンツ理解が優れていること

Foundry IQ は三層スタックで構成される。

1. **Foundry 統合レイヤー（最上位）**: UI 上での高生産性ワークフロー
2. **Knowledge Retrieval System（中間）**: Agentic Retrieval、複数ナレッジソース対応の反復クエリプランニング
3. **Core Retrieval Engine（基盤）**: Azure AI Search ベース、ベクトル検索＋レキシカル検索＋ステートオブアートランキングモデル、エンタープライズグレードのセキュリティ・スケーラビリティ

## ライブデモ：ファイルからナレッジベースを 1 分で作成（1:00頃）

登壇者は Azure AI Foundry の UI を開き、以下の手順をリアルタイムで実演した。

1. Foundry プロジェクト内の「Knowledge」セクションへ移動
2. 新規ナレッジベース「Movies Wiki」を作成（Wikipedia からダウンロードした映画記事数本をドラッグ＆ドロップ）
3. **すべてのナレッジベースは自動的に MCP サーバーとして公開される**ため、追加のサーバーセットアップは不要
4. GitHub Copilot の MCP 設定画面を開き、新しい MCP サーバーを追加

   - 設定内容の概要: URL末尾に `/mcp` を追加するだけで MCP エンドポイントとして機能する（`https://<foundry-iq-instance>.search.windows.net/knowledge-bases/<kb-name>/mcp?api-version=<new-version>`）
   - デモ途中で設定フォームが一度消えてしまうハプニングがあり、やり直した

5. GitHub Copilot から「Which pill did Neo take?」と質問 → Foundry IQ の MCP サーバーが応答し、「Neo took the red pill（Matrix より）」と正しく返答

デモを通じてコメントされた要点：「ゼロからファイルをアップロードし、MCP または API から接続できる稼働中のナレッジベースを作るまでに要する時間はほんの数分」

## Foundry IQ サーバーレス Public Preview 発表（9:00頃）

従来の Foundry IQ（Azure AI Search ベース）は「専用容量（Dedicated Capacity）」モデルを採用しており、安定した予測可能なワークロードには適しているが、「事前に必要容量を見積もらなければならない」という課題があった。これを解決するために、**サーバーレス Foundry IQ の Public Preview** を発表した。主な特徴は以下の通り。

- **作成時間**: 10〜20 秒でサービスが立ち上がる
- **コスト**: 利用するまで課金ゼロ、アイドル時はスケールtoゼロ（インデックスのストレージコストのみ）
- **本番対応**: 開発用途だけでなく本番環境でも利用可能
- **ダイナミック用途に最適**: エージェント自身がサービスを動的に作成・削除するシナリオや、ユニットテストのように頻繁にインデックスを作成・廃棄する用途に適している
- **技術基盤**: 既存の Foundry IQ スタックと同じステートオブアートの技術（最新ランキングモデル、即時 RAG スタック等）

サーバーレスと専用の使い分け目安：

| シナリオ | 推奨モード |
|---|---|
| 使用量ベースの課金を希望 | サーバーレス |
| 中〜小規模インデックスが多数 | サーバーレス |
| 開発・CI/CD・ユニットテスト | サーバーレス |
| エージェントが動的にインデックスを管理 | サーバーレス |
| 高予測性・安定した大規模ワークロード | 専用 |
| コンフィデンシャルコンピューティング要件 | 専用 |

デモでは Foundry の UI と Azure ポータルの両方から作成できることを示した。また、エージェントが IMDb の CSV ファイルを参照し「新しい Foundry IQ サービスを作成してインデックスを作り、最初の 100 行をロードせよ」という指示を自律実行するデモも同時並行で動かし、数分後に Azure ポータルでサービス・インデックス・100 件のドキュメントが生成されていることを確認した。

## ナレッジソースの多様性とデータ取り込み（12:44頃）

ナレッジベースは「知識のスコープとポリシー（どのくらいの検索努力をかけるか、ステアリング指示など）」を定義するものであり、その下に複数のナレッジソースが存在する。

### ファイル（Files）
手元のファイルを直接アップロード。数十〜百ファイル程度に留まる場合向け。コーディングエージェントのローカルファイルアクセスと似た感覚で使えるが、数百万 PDF は現実的でない。ファイルアップロード後は自動でコンテンツ抽出・ベクトル化・インデックス化が行われる。

### Azure Blob Storage・OneLake 等（オブジェクトストア連携）
アプリが内部管理するコンテンツを BLOB ストレージや OneLake に格納している場合、Foundry IQ を向けるだけで自動インジェストパイプラインが組み上がる。デフォルトでチャンキング・ベクトル化・インデックス化を実施し、増分同期（変更追跡）により常に最新のサーチインデックスを維持する。カスタムステップの注入も可能。マルチメディア（動画・音声等）にも対応。

### Azure Content Understanding との統合（コンテンツ抽出品質）
高品質なコンテンツ抽出のため **Azure Content Understanding** と統合されている。OCR・ドキュメントレイアウト解析・読み順保持・複数カラム対応・手書きテーブルの抽出（チェックボックスまで認識）・画像の言語化（image verbalization）などが自動で行われる。スキーマを指定して特定フィールドのみを抽出させることも可能。

### Work IQ（Microsoft 365 テナントデータ）
テナント管理者の同意を得るだけで M365 テナント内（SharePoint、メール、カレンダー等）へ直接アクセス可能。設定はほぼ不要。

### Fabric IQ（Microsoft Fabric のアナリティクスデータ）
Fabric の OneLake カタログ全体（レイクハウス、データウェアハウス、セマンティックモデル、Data Agent、オントロジーなど）と統合。Natural Language to SQL（Fabric の Data Agent 機能を活用）を経由してクエリし、結果を検索ワークロードに統合。デモでは「Movie Stats」という名前で映画の評価・統計データ（Parquet ファイル）を管理する Fabric Data Agent をナレッジソースとして追加した。

### Web IQ（Web 検索）
Build 2026 前日に発表された **Web IQ**（Public Preview）。MCP サーバー経由で接続し、Web 検索ツールを指定するだけで Web グラウンディングが可能になる。

### MCP サーバー（カスタム拡張）
上記のいずれにも当てはまらないデータソースや既存アプリに対しては MCP サーバー経由で接続できる。Foundry IQ は MCP の出力をヒューリスティックでアイテム指向リストに変換し、さらに独自ランキングシステムで関連性を向上させる。例: GitHub MCP サーバーの Issue をナレッジソースとして取り込む。

## セキュリティ：ドキュメントレベルアクセス制御と Purview 連携（27:12頃）

企業内データへのアクセスコントロールは後付けではなく、スタックの底部で標準実装されている。

- **Entra 統合によるドキュメントレベルセキュリティ**: SharePoint や BLOB ストレージ（階層型名前空間有効）など ACL をサポートするソースからのアクセス制御情報を検索インデックスに伝播。グループメンバーシップも考慮。クエリ時にユーザーの委任トークンを提示するだけで、そのユーザーが閲覧可能なドキュメントのみがヒットする。セキュリティはスタックの底部で強制されるため、アプリケーション側での実装が不要。
- **Microsoft Purview との統合**: 機密ラベル（sensitivity labels）が付いたドキュメントは通常の索引ツールでは暗号化されているため読み取れないが、Purview 連携でインデックス化かつセキュアに管理可能。感度ラベルを構築する UI にも伝播できるため、Office と同等のラベル体験を独自アプリに持ち込める。
- 完全なサンプル実装がリリース済み。

## Agentic Retrieval 第 2 世代：品質・トークン効率の向上（31:00頃）

### パイプラインの流れ

1. エージェントからのクエリを受け取る
2. **クエリプランニング**: どのナレッジソースを使うか、クエリをどう分解するかを判断
3. 複数の検索を並行実行
4. 結果を評価し、必要なら**反復検索**（設定した「retrieval effort」に応じてイテレーション数を制御）
5. 最終結果をエージェントに返す（任意でアンサー合成も実施）

### 第 2 世代での改善内容

- **言語モデルの進化への対応**: 2025 年秋以降、モデルが大幅に向上（ツールコールループ等）。それに合わせてワークフロープロンプトを全面刷新
- **新しいセマンティックランカーの訓練**: ランキング品質の継続的向上
- **アンサー合成の大幅改善**
- **モデル固有プロンプト**: MCP パラメータバインディングなどのタスクでモデルごとに最適化されたプロンプトを使用

### 性能評価指標の改善

評価軸は再現率（recall）・正答率・完全性（completeness）・「知らない」誤回答率の複合指標。比較対象は BM25 レキシカルインデックス / ハイブリッド検索（ベクトル＋レキシカル） / Agentic Retrieval オフ（minimal モード）であり、**すべての指標で明確な改善**が確認された。

### トークン効率

より少ないトークンでより良い回答を達成するパレートラインを示した。プロンプト構築時にトークンキャッシング（プレフィックスキャッシュ）を意識した設計を採用し、レイテンシ短縮とコスト削減を実現。詳細な技術論文はサイエンスチームによって公開されているとのこと。

## 複合デモ：多ソース Agentic Retrieval とインデックス深掘り（37:00頃）

Wikipedia 記事（ファイルナレッジソース）、映画統計（Fabric Data Agent）、Web IQ（MCP 経由）の三つを組み合わせたナレッジベースに対して「トップ SF 映画の評価と興行成績を教えよ」に相当するクエリを実行した。

- オーケストレーションモデルとして GPT-4o mini を選択（アンサー合成のオン/オフ・ステアリング指示もオプションで設定可能）
- 実行ログには「プランナーが実行 → Fabric Data Agent にクエリ（トップ SF 映画の評価取得）→ Web MCP サーバーでボックスオフィス情報取得 → アンサー合成 → 完了」というステップが明示された
- 全参照元情報（どのナレッジソースから来たか、元ファイルリンク等）もレスポンスに含まれ、デバッグやエージェントへのフィードバックに活用可能

続けて Azure ポータルでインデックスの内部を確認するデモを実施。チャンク内容・ベクトル値・スキーマ（ベクトル検索の圧縮設定：デフォルト 8 ビット量子化、リランキングポリシー等）が詳細に設定・確認可能であることを紹介した。

### 超高速検索デモ（英語 Wikipedia 全文インデックス）

全英語 Wikipedia を格納した約 2200 万チャンクのインデックスに対してキーストロークごとのリアルタイム検索を実演した。「キー入力の速さについていけないほどの速度で検索が完了する」と述べ、「エージェントが 10〜20 クエリを並行で投げてもすべて 1 秒以内に返ってくる」と説明した。Agentic Retrieval（数秒〜最大 10 秒程度）とインデックス直接検索（即時）の使い分けが自由に行えると強調した。
