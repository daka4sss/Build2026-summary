## 全体像

本セッションは、オープンソースフレームワーク（LangChain / LangGraph）と標準プロトコル（MCP、A2A、OpenTelemetry）を使って構築したエージェントを、Microsoft Foundry でそのまま本番環境に持ち込む方法を、ライブデモ形式で段階的に実演するデモセッションである。

中心となるテーマは「エージェントをオープンソースで書いたとしても、本番デプロイのために書き直す必要はない」という点。LangGraph で記述したエージェントループをそのままに、Foundry の Hosted Agent 機能・OpenAI 互換 Responses API・OpenTelemetry トレース・A2A（Agent-to-Agent）プロトコルの各レイヤーがどう噛み合うかを一貫して示している。

デモはメールトリアージを題材に、（1）最小エージェント → （2）MCP接続 → （3）スキル追加 → （4）Playwright によるウェブ閲覧 → （5）Foundry Hosted Agent へのデプロイ → （6）OpenTelemetry トレース → （7）Copilot CLI / A2A による外部エージェントからの呼び出し、という7段階で構成されている。

## チャプター2: 最小エージェント — LangGraph + Foundry モデル（0:55頃）

### エージェントの本質はモデルとエージェントループ

Facundo が「Foundry も魔法のプラットフォームも使わずにエージェントを作るとしたら最小限のコードは何か？」と問いかける。

Nakumar の答えは「**モデルとエージェントループ**」。

- **エージェントループ**：モデルに次のステップを問い合わせ、ツールが必要なら実行し、その結果をもとに次を決定するサイクル
- 実装は意図的に最小限。`init_chat_model`（LangChain）でモデルを取得し、`create_react_agent`（LangGraph）でループを構築

### Foundry モデルは OpenAI 互換 API で提供

重要なポイントとして、Foundry が公開するほぼすべてのモデルは **OpenAI 互換 API** を通じて提供される。そのため、LangChain のコードは Foundry モデルを「OpenAI モデルと同じプロトコル」で呼び出せる。

> **モデルのターゲット切り替えはコードの書き直しではなく設定変更（configuration）だけで済む**

実演：`say hello` を送信すると、エージェントが応答を返すことを確認。

## チャプター3: MCP によるツール接続 — Work IQ Mail（2:14頃）

### エージェントに「手」を持たせる

エージェントがモデルの知識範囲内でしか動けない状態を超えるために、オープンソースの標準プロトコル **MCP（Model Context Protocol）** を導入する。

- MCP はエージェントがツールを**ランタイムに発見して呼び出す**ためのオープンプロトコル
- このデモで使う MCP サーバーは **Work IQ Mail**。Microsoft 365 のメール機能をツールインターフェイス経由で提供する

### コード変更は最小限

エージェントのコードは基本的に同じ LangGraph スタイルのまま。変更点は「MCP サーバーの URL を渡してツールとして追加する」だけ。ツールスキーマ例：`search_messages`、`get_message_details`、`draft_replies` など。

エージェントは Microsoft 365 のすべての HTTP エンドポイントを知る必要はなく、MCP サーバーに接続してツール一覧を取得するだけでよい。

### デモ実行

「メールを確認して」というプロンプトを送信。エージェントがランタイムにメールツールを発見し、適切なツールを選択して実行。Work IQ MCP サーバー経由で **5通のメール**を取得。

しかし Facundo は「メールの未読一覧を取得するだけでは時間の節約にならない。インボックスのトリアージをしてほしい」と指摘し、次のステップへ。

## チャプター4: スキル — エージェントへの「プレイブック」付与（4:33頃）

### ツールとスキルの違い

- **ツール（Tool）**：動詞（Verb）。単一の操作。例：`search_messages`
- **スキル（Skill）**：プレイブック（Playbook）。複数ステップの指針。例：「インボックスのトリアージ」

スキルは「メールを取得し、カテゴリに分類し、優先度を付け、必要なら返信草稿を作る」という一連の手順を定義する。

### スキルはただのマークダウン

**重要なポイント：スキルは特別なサービスでも独自スキーマでもなく、単純な Markdown ドキュメント**。

- 小さなフォーマットブロックを含む Markdown ファイル
- エージェントが仮想スキルパス（virtual skills path）にマウントされたスキルフォルダを参照できる
- プロンプトが関連するときにエージェントが自律的にスキルを読み込む

### デモ実行

「インボックスをトリアージして」と送信。今回は複数のツール呼び出し（`get_message` で各メールの本文取得 → 分類）が走り、最終的にトリアージサマリーを返す。内容：カテゴリ（緊急・要対応・参考等）、推奨アクション、各アクションの理由。

Facundo のコメント：「同じモデル、同じツールでも、スキルがあるだけで動作が全く変わる。スキルは大量のシステムプロンプトに頼らず、エージェントの動作を再現可能にする軽量な方法だ。」

## チャプター5: Playwright によるウェブブラウズ能力の追加（6:52頃）

### ブラウズ機能の追加アプローチ

汎用エージェントの特徴の一つが「ウェブブラウズ」。これをオープンソース技術で実現する方法として **Playwright** を選択。

なぜ MCP サーバーではなく CLI ツールか？

- ブラウザ操作向け MCP サーバーはツールサーフェスが大きくなりがち
- Playwright CLI はシグネチャが 1 つの `arc` 文字列 + オプションのブラウザセッションのみ
- スナップショットやコマンド詳細はエージェントが要求したときのみコンテキストウィンドウに入る
- **トークン効率が高い**（MCP サーバーの大きな JSON スキーマを毎回取得する必要がない）

実装上は、既存の `get_tools()` メソッドに Playwright ツールを追加するだけ。

### デモ実行（ハプニングあり）

「Amazon を開いて最初の Microsoft ブランドのコーヒーカップの値段を教えて」と送信。ウェブブラウズスキルを発見し、Playwright CLI ツールを呼び出してブラウズを実行した。しかし結果は「**Microsoft ブランドのカップは見つからなかったが、Microsoft 以外の最初のマグカップが $16.19 だった**」という回答。

Facundo：「何が起きたかはわからないが、トレースを確認すれば理由がわかる（笑）」——これは本番向けのトレーシングの必要性への伏線になっている。

## チャプター6: Foundry Hosted Agent へのデプロイ（9:09頃）

### 本番環境への課題

「ターミナルで動くのはわかった。でも本番ユーザーは自分のノートパソコンに SSH したくはない」（Facundo）

### Foundry が提供するもの

Microsoft Foundry は、**同じ LangGraph エージェントをそのまま Hosted Agent としてホスト**し、**OpenAI 互換 Responses API** 経由で公開する。

アダプター層（`agent_server.py` 的なファイル）の構成：

1. `build_agent()` — 既存のエージェントをそのまま呼び出す（コードの再利用）
2. **Responses Host Server** — LangGraph エージェントを Responses 互換エンドポイントとして公開
3. **Foundry Server Host の初期化をグラフ構築前に実行** — OpenTelemetry の LangChain インスツルメンテーションをグラフ構築前にアタッチするため（重要な順序制約）

重要な設計原則：
- **同じコードがローカルでもクラウドでも動く**（環境による書き分けは不要）
- ラッピングは「プロトコル変換」のみ。エージェントロジック自体は一切変更しない

デモ：デプロイ済みのエージェントに「インボックスをトリアージして」を送信。エージェントが実行を開始する。

## チャプター7: OpenTelemetry による可観測性（11:02頃）

### 本番運用での課題

デプロイしたエージェントが期待通りの回答を返さないとき、何が起きたかを知る手段が必要。

### Foundry + OpenTelemetry の統合

Foundry は **Application Insights** と **OpenTelemetry** に統合されており、以下を計装（instrumentation）できる：

使用技術：
- **Microsoft OpenTelemetry Distro**
- **OpenTelemetry GenAI セマンティックコンベンション**（業界標準の AI 用スパン定義）

観測できる情報：
- LangGraph のスパン（グラフの各ノード実行）
- モデル呼び出しの詳細
- レイテンシ
- 入力・出力のキャプチャ
- 各スパンのトークン使用量

### Foundry トレース UI

Foundry の「Traces」タブでリクエスト一覧を確認可能。歴史的なトレースを開くと：
- ユーザーの入力・出力
- 各ツール呼び出しの詳細（invoke_agent スパン、chat スパン等）
- スキルを読み込むためのツール呼び出し
- 各セクションのトークン消費量

Facundo のポイント：「本番に移行して初めてわかるのが、エージェントの時間とコストがどこに消えているかだ。各セクションのトークン消費量を把握することで、改善・最適化のターゲットが明確になる。」

### オープンスタンダードの価値

OpenTelemetry は業界で広く採用されたオープンスタンダードなので、Foundry の UI に限らず **Grafana** や他の観測ツールにも同じデータを流せる。ベンダーロックインなし。

## チャプター8: A2A（Agent-to-Agent）プロトコルによるエージェント間連携（13:01頃）

### 2026年はエージェント間連携の時代

Facundo：「2026年のトレンドはエージェントが他のエージェントを呼び出すことだ。先ほどデプロイしたエージェントを別のエージェントから利用できるか？」

### Foundry Hosted Agent が自動的に A2A エンドポイントを公開

Microsoft Foundry にエージェントをホストすると、**A2A（Agent-to-Agent）互換のエンドポイント**が自動的に付与される。

A2A 互換クライアントはこのエンドポイントを使って：
1. **エージェントカード（Agent Card）** を発見（エージェントの能力・API記述）
2. ホスト済みエージェントへメッセージを送信

### Copilot CLI による呼び出しデモ

Copilot CLI（全く別のランタイム）を使ったデモ。

Copilot CLI 側の設定：A2A ディレクトリを MCP サーバー形式で公開し、`search_agent` ツールと `call_agent_a2a` ツールの 2 つを提供。

実行フロー（全コンポーネントが疎結合で連携）：
1. Copilot CLI が「インボックスをトリアージして」を受け取る
2. MCP サーバー（A2A ディレクトリ）を通じてエージェントを検索
3. トリアージタスクを実行できるエージェントを1つ発見
4. **A2A プロトコル**経由でそのエージェントを呼び出す
5. 呼び出された Foundry Hosted Agent（LangGraph 実装）が起動
6. Work IQ MCP サーバー経由でメールを取得
7. スキル（triage-inbox.md）を読み込んでトリアージを実行
8. 結果を A2A レスポンスとして Copilot CLI に返す
9. Copilot CLI がユーザーに回答を表示

Nakumar：「美しいのは、これらのコンポーネントが互いを知らないという点だ。それぞれが独立して動いており、オープンな標準インターフェイスを介して構成されている。」

## まとめ

### セッションのメッセージ

本セッションが伝えたかったオープンソースストーリーを一言で表すと：

### デモで示された技術スタックの構成要素

| 役割 | 技術 | 種別 |
|------|------|------|
| エージェントフレームワーク | LangGraph（LangChain） | オープンソース |
| モデル接続 | OpenAI 互換 API | オープンプロトコル |
| ツール接続 | MCP（Model Context Protocol） | オープンプロトコル |
| ツール定義（M365） | Work IQ Mail MCP Server | Microsoft 提供 |
| ウェブブラウズ | Playwright CLI | オープンソース |
| エージェント記述 | スキル Markdown | 独自なし（テキスト） |
| ホスティング | Microsoft Foundry Hosted Agent | Azure |
| エンドポイント公開 | OpenAI Responses API 互換 | オープンプロトコル |
| 可観測性 | OpenTelemetry + Application Insights | オープン標準 |
| エージェント間連携 | A2A（Agent-to-Agent）プロトコル | オープンプロトコル |

### 発表された新機能・機能詳細

1. **Microsoft Foundry Hosted Agents** — LangGraph エージェントを Responses API 互換のホスト済みエンドポイントとして公開する機能（デモで実演済み。GA/Preview ステータスは本セッション内で明言なし）
2. **A2A エンドポイントの自動付与** — Foundry にホストしたエージェントが自動的に A2A 互換エンドポイントを持つ（デモで実演済み。ステータス明言なし）
3. **Work IQ MCP Server** — Microsoft 365 メール・カレンダー・Teams のツール接続（デモ利用として紹介。ステータス明言なし）
4. **OpenTelemetry GenAI セマンティックコンベンションのサポート** — Foundry の Traces UI でエージェントのスパン・トークン・レイテンシを確認可能（デモで実演済み）
5. **スキル（Skill）パターン** — Markdown ドキュメントをエージェントのプレイブックとして活用する設計パターン（OSS・Foundry 共通）
